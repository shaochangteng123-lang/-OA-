# 09 - 服务集成模块

## 模块概述

服务集成模块负责与外部第三方服务的集成，主要包括飞书（Feishu/Lark）OAuth 认证和 API 调用，以及 Notion 集成（如适用）。

## 主要功能

### 1. 飞书集成

- OAuth 2.0 登录
- 用户信息获取
- Access Token 管理
- API 调用封装

### 2. Notion 集成（可选）

- Notion API 集成
- 数据同步
- 内容导入导出

### 3. Token 管理

- Access Token 获取
- Token 刷新
- Token 缓存

### 4. API 封装

- 统一的 API 调用接口
- 错误处理
- 重试机制

### 5. 节假日通知集成

- 自动搜索中国政府网政策库中的国务院办公厅年度节假日通知
- 抓取通知正文并解析放假日、调休上班日
- 将结果写入 `holidays` 表供日历、日志、请假和周报任务统一使用

### 6. 本地发票 OCR（文字识别）

- 使用 `pdftohtml` 提取电子发票文字坐标
- 坐标提取时忽略 PDF（便携式文档格式）内嵌图片，避免在上传临时目录生成无业务引用的旁生图片
- 无文字层时回退到图片 OCR（文字识别）流程
- `*预付卡销售*` 类发票会继续识别后缀项目；交通卡、一卡通、公交卡、地铁卡、乘车卡等充值、储值、加值项目归类为交通储值卡，供基础报销月度交通额度判断使用

### 7. 入职邀请函工资识别

- [server/services/invitationSalaryOcr.ts](../server/services/invitationSalaryOcr.ts) 只处理正式入职邀请函第一页，第二页重复内容不参与识别
- 优先通过 `pdftotext` 读取文字层；无法识别时使用 `pdftoppm` 只转换第一页，再调用本地 PaddleOCR（飞桨文字识别）
- 优先匹配“原则每月发放”，并兼容“月度税前工资”“每月税前工资”“月保障薪酬”等表述
- 同时识别出年工资时校验其是否等于月工资乘以 12，防止误把固定部分或浮动部分当作完整月工资
- 识别失败返回业务结果，不阻止正式入职邀请函文件归档；识别过程不在日志中输出工资原文

### 8. 人事档案类型识别

- [server/services/employeeDocumentClassifier.ts](../server/services/employeeDocumentClassifier.ts) 逐页识别十种固定人事档案首页，并识别离职证明、职业资格材料及通用资料标题等“其他”页段边界
- [server/services/employeeDocumentBundle.ts](../server/services/employeeDocumentBundle.ts) 按首页边界归组连续页面，并将每种类型拆成独立文件
- 每页优先读取 PDF（便携式文档格式）文字层；扫描件只转换当前页，再调用本地 PaddleOCR（飞桨文字识别）
- 正式标题用于识别新页段；标题漏识别时，邀请函、入职申请表、劳动合同、保密协议、个人声明、电脑管理办法、身份证、体检报告、学历证书和银行卡均可通过各自的正文组合特征确认首页
- 扫描件低分辨率识别出可疑“其他”标题时，会提高分辨率复核一次；复核仍不能匹配固定类型后才归入“其他”，避免把“达成如下协议”等正文误当成资料名称
- 类型顺序不固定；缺失类型不生成记录，同一类后续无标题页面沿用当前类型，遇到其他资料标题后切换到“其他”
- 单独上传且完全无法匹配固定十类的有效文件整份归入“其他”；“附件”开头的合同内嵌标题不会被误拆成其他资料
- 同一整册出现多份额外材料时按各自边界分别拆分，数据库类型统一为“其他”，展示文件名保留识别到的资料名称
- 图片识别和拆分临时文件在处理后清理；分类过程不记录档案正文，避免身份证、银行卡和合同内容进入服务器日志

### 9. 劳动合同期限与工资同步

- [server/services/employmentContractOcr.ts](../server/services/employmentContractOcr.ts) 优先读取劳动合同前四页文字层，扫描件按第二页、第一页、第三页、第四页顺序执行 OCR（文字识别）
- 在“劳动合同期限”条款内提取起止日期；同时存在试用期时选择跨度最长的正式合同期限，并兼容扫描日期中的下划线及常见误识别
- 同步解析每份合同“试用期”条款中的截止日期；续签合同试用期栏位为空时返回空值
- 合同归档后以第一份已识别合同维护员工入职日期和试用期截止，以结束日期最晚的一份维护当前合同；续签不会覆盖入职或试用期日期
- 没有合同或合同期限识别失败时不使用账号创建时间、手填日期或固定月份推算，员工入职日期保持为空
- [server/services/payrollRecordSync.ts](../server/services/payrollRecordSync.ts) 统一同步当前及未来月份工资；涨薪起算日优先使用最早一份已识别合同的开始日期，没有合同数据时才回退入职日期
- 工资同步服务联查账号角色，BOSS和超级管理员不生成或更新工资记录
- 正式邀请函上传会重置本月工资手工标记；合同新增、删除触发的自动重算保留管理员手工工资、缴费基数和个税

### 9.1 人力成本银行回单与个税明细识别

- [server/services/humanCostReceiptOcr.ts](../server/services/humanCostReceiptOcr.ts) 复用银行回单金额识别底座，独立处理人力成本文件，不写入报销回单批次或待认领数据
- 图片文件直接执行 OCR（文字识别）；PDF（便携式文档格式）先按页转换为图片，并复用工行同页上下两笔回单的结构分析和切分能力
- 每一笔候选回单均调用财务区审批中心相同的付款回单解析和真实性校验，缺少银行、回单、金额、收款人、账号或银行特征字段时不进入汇总
- 实发工资额外校验摘要、用途、备注或客户附言中的工资语义；一个 PDF（便携式文档格式）中的非工资回单会被明确忽略，不计入失败笔数
- 实发工资在至少识别出一笔有效工资回单后直接返回已识别，不再因同一文件的其他失败片段进入待核对；工资语义判断先于银行回单字段校验，避免无关内容产生误报
- 通过校验的工资回单返回收款人、收款账号、金额、电子回单号、页码和上下位置；业务路由优先按完整账号、其次按户名精确匹配员工，同名时保持待核对
- 多笔金额先转为整数分再求和，避免 JavaScript（脚本语言）浮点误差；全部、部分和全部失败分别返回 `recognized`、`partial`、`failed`
- 识别用临时图片在处理结束后立即清理，数据库不保存 OCR（文字识别）全文；单笔工资关联仅保存预览定位所需字段
- 所有回单识别任务通过进程内去重串行队列执行，避免页面轮询把同一历史回单重复提交；任务异常后短暂熔断后续识别，不阻塞登录和普通接口
- OCR（文字识别）常驻子进程超时或服务关闭时使用强制终止，确保旧模型释放后才允许后续任务启动，避免多个模型同时占用资源
- [server/services/payrollTaxDetailOcr.ts](../server/services/payrollTaxDetailOcr.ts) 复用同一 OCR（文字识别）常驻进程的文字框坐标；先定位“应纳个税”表头的真实横坐标，再按工资表中的员工姓名逐行提取交叉单元格
- “住房公积金 应纳个税”等合并识别表头按字符比例还原“应纳个税”中心位置；员工行在该列没有文字框时按空白单元格填 0，列内有无法解析文字时不误填并返回未识别名单
- PDF（便携式文档格式）个税明细先逐页转换为图片，最多支持 30 页；同一员工重复出现且金额不一致时拒绝批量回填，避免覆盖为不确定结果

### 10. 入职模板员工编号、合同日期与职位写入

- [server/services/onboardingTemplateNumber.ts](../server/services/onboardingTemplateNumber.ts) 使用 `pdftohtml（PDF 文字坐标提取工具）` 逐页读取文字、坐标和字体颜色，再使用 `pdf-lib（PDF 处理库）` 写入当前员工编号
- 入职邀请函处理全部页面；劳动合同书第 1 页处理右上角黑色编号，第 2 页起处理左上角蓝色“合同编号”；新员工入职申请表只处理第 1 页
- 劳动合同书额外定位“劳动合同期限”和“试用期”行中的年月日空位，按员工模板拟定日期分别写入合同起止和可选试用期起止日期
- 劳动合同书识别第二页第四条“担任……岗位”中的示例职位区域，向左扩展覆盖示例文字的抗锯齿边缘后写入员工当前职位，并保留完整的“担任”、下划线和前后正文
- 自动写入的数字使用相邻“年、月、日”文字的实际字号，并向上调整基线，与正文大小一致且不贴近模板下划线
- 离职模板首先使用系统文字定位工具读取字段，异常 PDF（便携式文档格式）自动回退到 PDF.js（PDF 解析器）；编号基于每页原完整编号的真实字形框覆盖，不复用其他页面坐标
- 中文职位通过高分辨率透明图层写入，使用容器内置中文字体并按职位空位自动缩放；下划线保持与相邻汉字基线对齐，通过上移自动职位文字留出清晰间距
- [server/services/contractTemplateCycle.ts](../server/services/contractTemplateCycle.ts) 在正式劳动合同归档事务中清空四个新周期拟定日期；下载随即锁定，预览保留最新版模板的空白日期，第四条岗位仍使用员工当前职位
- 三类模板上传时逐页试写示例编号；劳动合同书同时试写示例日期和职位，缺少目标位置、文件加密或页面旋转异常时直接拒绝保存
- 自动写入编号只用于员工下载入职模板；管理员上传至 `employee_documents` 的历史或正式人事档案不调用本服务
- 管理员预览模板时返回原模板，员工下载时生成带当前编号和拟定日期的临时副本；原模板和管理员上传的人事档案内容、编号及文件名均不改写
- 员工编号由 ASCII（美国信息交换标准代码）字符组成，使用内置无衬线字体写入，不需要加载中文字体

### 10.1 离职档案识别与模板处理

- [server/services/resignationDocumentClassifier.ts](../server/services/resignationDocumentClassifier.ts) 逐页识别五类离职档案首页，优先读取文字层，扫描件回退至共用 PaddleOCR（飞桨文字识别）进程；标题按中文主体归一化匹配，兼容全角或半角分隔符、空格、标题前置填充文字及少量识别误差
- [server/services/resignationDocumentBundle.ts](../server/services/resignationDocumentBundle.ts) 不限制五类材料的排列顺序；每识别到一个材料首页标题便开始新的页面分段，直至下一个首页标题出现，同类重复分段会合并
- 文件起始页确实没有五类材料首页标题时拒绝自动归档并返回页码，避免把封面或无关资料错误并入后续档案
- [server/services/resignationArchive.ts](../server/services/resignationArchive.ts) 统一计算五类当前档案完成度；上传阶段只返回是否齐全，管理员显式确认后才事务更新离职记录、员工状态、原账号状态和审计日志
- [server/services/resignationTemplatePdf.ts](../server/services/resignationTemplatePdf.ts) 直接读取当前 PDF（便携式文档格式）模板；历史 DOCX（开放 XML 文字处理文档）固定转换为 PDF 后继续兼容，再以不可重排的原页面为底图叠加编号、自动字段和管理员自定义文字
- 历史 DOCX（开放 XML 文字处理文档）转换时不改写原上传文件，并按原文件页数清理转换器产生的空白尾页
- PDF（便携式文档格式）通过原整段编号的实际宽度精确计算完整编号遮罩范围，保留原“编号：”并统一重绘 `YULI-CS员工数字-LZ序号`；员工编号数字不足三位时左侧补零
- 服务同时读取原模板文字片段的字体名称、字号和颜色，自动字段以同一字体高度渲染；窄字段按实际字形边界横向适配并在左右保留安全区，不再通过缩小字号造成贴图感或裁掉最后一个字符
- 首次劳动合同日期来自合同历史中最早开始的一份；任职年限按首次合同日期至离职日期之间已经完整经过的自然月计算
- [src/components/resignation/ResignationTemplateEditor.vue](../src/components/resignation/ResignationTemplateEditor.vue) 使用 PDF.js（PDF 渲染库）逐页显示同一份原模板，并在服务端返回的位置上提供自动字段修改和自定义文字拖放
- [server/services/resignationTemplateFile.ts](../server/services/resignationTemplateFile.ts) 对新上传模板同时校验 `.pdf` 扩展名、`application/pdf` 媒体类型和 `%PDF-` 文件头；旧 DOCX（开放 XML 文字处理文档）识别逻辑仅用于兼容历史数据
- 在线草稿绑定具体模板版本；管理员更新模板后不会错误沿用旧模板的编辑内容

### 11. 转正申请单自动生成与内部电子签名

- [server/services/probationApplicationPdf.ts](../server/services/probationApplicationPdf.ts) 以管理员上传的转正申请表 PDF（便携式文档格式）为底稿，在固定表格位置叠加员工数据、在线填写内容、审批意见和签名
- [src/views/ProbationApplication.vue](../src/views/ProbationApplication.vue) 以独立页面承载员工填写和本人签名；转正状态页只负责展示和跳转，不再用弹窗嵌入整张申请单
- [src/components/probation/ProbationTemplateEditor.vue](../src/components/probation/ProbationTemplateEditor.vue) 使用 PDF.js（PDF 渲染库）直接显示同一份管理员原始模板，并在相同坐标提供员工述职、审批意见和签名回填区域；前端不再绘制另一套申请表
- 员工提交时自动填写申请人、所属部门、岗位职务、入职日期、申请日期和转正定岗；岗位职务与转正定岗均使用提交时的职位快照
- 本人述职、主管意见、人事部意见和总经理意见按当前申请版本写入，长文本自动换行并限制在各自表格区域
- 员工和总经理预先保存本人签名；管理员可在个人设置分别保存本人签名与代管的总经理签名。浏览器与服务器共用 [server/utils/signature-pixel-processing.ts](../server/utils/signature-pixel-processing.ts)，按局部背景差提取细笔画，再按连通区域的面积、密度、笔画宽度和边缘接触情况排除强阴影、暗块及纸张颗粒，裁剪后统一转换为 PNG（便携式网络图形）；[server/utils/electronic-signature.ts](../server/utils/electronic-signature.ts) 继续负责数据地址、真实文件头、大小和服务器落库前的二次校验
- [src/utils/personalSignature.ts](../src/utils/personalSignature.ts) 按本人或总经理类型读取当前账号在个人设置中保存的签名；签名栏初始保持空白，点击“签名”后才调用。管理员同时保存两类签名时先选择签名人，未保存任何可用签名时只提示前往个人设置
- 个人签名保存和转正签署记录使用不同文件：提交时复制当前签名形成申请版本快照，个人签名后续更新或删除不影响已经签署的申请单
- 转正路径固定为员工签名提交、总经理签署主管领导意见、管理员签署人事部意见、管理员代签最终总经理审批；管理员可选择本人签名或代管的总经理签名
- 签署记录同时保存实际登录操作人与申请单签名人；服务器依据签名类型读取受保护文件，客户端不能提交任意图片冒充已保存签名
- 每个签署日期使用服务器记录的实际签名时间，不能由客户端指定或修改
- 转正结论只在管理员完成最终审批后生成，其中职工自动填写员工姓名，拟定岗位和执行岗位自动填写职位，结论日期自动填写最终审批签名日期
- 正式文件生成成功后才写入转正档案；任一前置签名缺失、申请版本不一致或底稿不存在时拒绝生成，避免形成不完整正式文件
- 当前签名是带身份、意见、时间和版本审计记录的企业内部图片电子签名，不包含 CA（证书颁发机构）数字证书、可信时间戳或第三方存证

## 飞书集成

### 环境变量配置

```bash
# 飞书应用配置
FEISHU_APP_ID=cli_xxxxxxxxxxxx
FEISHU_APP_SECRET=your_app_secret
FEISHU_REDIRECT_URI=http://localhost:8899/login/callback
```

### OAuth 登录流程

#### 1. 获取登录 URL

```typescript
// server/services/feishu.ts
export const getFeishuLoginUrl = () => {
  const params = new URLSearchParams({
    app_id: process.env.FEISHU_APP_ID!,
    redirect_uri: process.env.FEISHU_REDIRECT_URI!,
    state: generateRandomState(), // 防 CSRF
  });

  return `https://open.feishu.cn/open-apis/authen/v1/index?${params}`;
};
```

#### 2. 处理回调

```typescript
export const handleFeishuCallback = async (code: string) => {
  // 1. 获取 access_token
  const tokenResponse = await fetch(
    "https://open.feishu.cn/open-apis/authen/v1/access_token",
    {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        grant_type: "authorization_code",
        client_id: process.env.FEISHU_APP_ID,
        client_secret: process.env.FEISHU_APP_SECRET,
        code,
      }),
    },
  );
```

```typescript
export const handleFeishuError = (error: any) => {
  if (error.code === 99991663) {
    throw new FeishuAPIError("Token 已过期", error.code);
  }

  if (error.code === 99991668) {
    throw new FeishuAPIError("应用权限不足", error.code);
  }

  throw new FeishuAPIError(error.msg || "未知错误", error.code);
};
```

### 重试机制

```typescript
export const retryFeishuAPI = async <T>(
  fn: () => Promise<T>,
  maxRetries = 3,
): Promise<T> => {
  let lastError: Error;

  for (let i = 0; i < maxRetries; i++) {
    try {
      return await fn();
    } catch (error) {
      lastError = error as Error;

      // 如果是 token 过期，清除缓存重试
      if (error instanceof FeishuAPIError && error.code === 99991663) {
        cachedTenantToken = null;
      }

      // 等待后重试
      await new Promise((resolve) => setTimeout(resolve, 1000 * (i + 1)));
    }
  }

  throw lastError!;
};
```

```typescript
// 验证飞书事件签名
export const verifyFeishuSignature = (
  timestamp: string,
  nonce: string,
  encryptKey: string,
  body: string,
  signature: string,
): boolean => {
  const data = `${timestamp}${nonce}${encryptKey}${body}`;
  const hash = crypto.createHash("sha256").update(data).digest("hex");

  return hash === signature;
};

// 处理飞书事件

  switch (event.type) {
    case "url_verification":

    case "event_callback":
      // 处理具体事件
      await processFeishuCallback(event.event);
      return { success: true };

    default:
      console.warn("未知的飞书事件类型:", event.type);
      return { success: false };
  }
};
```
