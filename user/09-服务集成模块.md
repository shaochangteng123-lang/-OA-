# 09 - 服务集成模块

## 模块概述

服务集成模块负责与外部第三方服务的集成，主要包括飞书（Feishu/Lark）OAuth 认证和 API 调用，以及 Notion 集成（如适用）。

## 主要功能

### 1. 飞书集成

- OAuth 2.0 登录
- 用户信息获取
- Access Token 管理
- API 调用封装

### 2. Notion 集成（可选）

- Notion API 集成
- 数据同步
- 内容导入导出

### 3. Token 管理

- Access Token 获取
- Token 刷新
- Token 缓存

### 4. API 封装

- 统一的 API 调用接口
- 错误处理
- 重试机制

### 5. 节假日通知集成

- 自动搜索中国政府网政策库中的国务院办公厅年度节假日通知
- 抓取通知正文并解析放假日、调休上班日
- 将结果写入 `holidays` 表供日历、日志、请假和周报任务统一使用

### 6. 本地发票 OCR（文字识别）

- 使用 `pdftohtml` 提取电子发票文字坐标
- 坐标提取时忽略 PDF（便携式文档格式）内嵌图片，避免在上传临时目录生成无业务引用的旁生图片
- 无文字层时回退到图片 OCR（文字识别）流程
- 车辆租赁免税发票的开票名称跨行时，续行解析会跳过数量、金额、税率“免税”和税额占位符，只拼接项目名称列的真实续文；两个独立识别通道均明确识别到免税／不征税且税额均为空时，按免税票面事实完成复核。首次财务登记、已有登记补充发票和历史兼容路径均继续保存真实空税额，不伪造为零；详情回读保持空值。发票号码、日期、价税合计和购销主体仍须逐项一致。
- `*预付卡销售*` 类发票会继续识别后缀项目；交通卡、一卡通、公交卡、地铁卡、乘车卡等充值、储值、加值项目归类为交通储值卡，供基础报销月度交通额度判断使用

### 7. 入职邀请函工资识别

- [server/services/invitationSalaryOcr.ts](../server/services/invitationSalaryOcr.ts) 只处理正式入职邀请函第一页，第二页重复内容不参与识别
- 优先通过 `pdftotext` 读取文字层；无法识别时使用 `pdftoppm` 只转换第一页，再调用本地 PaddleOCR（飞桨文字识别）
- 优先匹配“原则每月发放”，并兼容“月度税前工资”“每月税前工资”“月保障薪酬”等表述
- 同时识别出年工资时校验其是否等于月工资乘以 12，防止误把固定部分或浮动部分当作完整月工资
- 识别失败返回业务结果，不阻止正式入职邀请函文件归档；识别过程不在日志中输出工资原文

### 8. 人事档案类型识别

- [server/services/employeeDocumentClassifier.ts](../server/services/employeeDocumentClassifier.ts) 逐页识别十种固定人事档案首页，并识别离职证明、职业资格材料及通用资料标题等“其他”页段边界
- [server/services/employeeDocumentBundle.ts](../server/services/employeeDocumentBundle.ts) 按首页边界归组连续页面，并将每种类型拆成独立文件
- 每页优先读取 PDF（便携式文档格式）文字层；扫描件只转换当前页，再调用本地 PaddleOCR（飞桨文字识别）
- 页面最靠前的精确主标题优先于正文组合特征；正文或附件中出现其他材料名称时不会覆盖当前首页主类型，组合文件名也不参与具体页分类
- 标题漏识别时，邀请函、入职申请表、劳动合同、保密协议、个人声明、电脑管理办法、身份证、体检报告、学历证书和银行卡均可通过各自的强正文组合确认首页；个人声明兼容“本人谨此声明”“特此声明”“姓名”和个人资料真实有效等特征
- 扫描件先使用 300 DPI（每英寸点数）页面上部标题区执行快速筛查；快速结果没有边界时，再对页面中央主标题区域放大识别，聚焦结果只接受固定档案的精确标题，不接受正文组合、印章噪声或通用“其他资料”猜测；完成这层复核后，文字充分、平均置信度达标且仍无边界的页面才判定为续页，证据不足、候选冲突或证件类页面继续执行 480 DPI（每英寸点数）标题增强及 300 DPI（每英寸点数）整页兜底
- 扫描图像本身横置时，系统根据 OCR（文字识别）文字框长轴识别方向异常；正常页面仍只走原快速路径，只有纵向文字框证据充分的异常页才复用一次整页渲染并按 90°、270°补查，倒置文字继续由识别引擎已有的行方向校正处理，避免普通少字续页误触发多方向识别
- 多方向与多分辨率结果按证据强度合并：精确首页标题优先于正文组合；学历、身份证和银行卡等结构唯一的证件只有 90°、270°两路得到同一类型时才允许使用组合证据，合同、申请表、保密协议等仍要求精确标题；两个不同精确标题或固定标题与明确“其他资料”标题冲突时继续拒绝归档；拆分前后均校验源页必须恰好出现一次，存在漏页、重复页或越界时停止落库
- 劳动合同、保密协议和个人声明即使快速结果一致也保留 480 DPI（每英寸点数）增强确认；低风险类型只有两种文字排序均得到前置精确标题、完整正文结构且不存在竞争类型时才省略增强轮，不同固定类型候选一律转为不确定页
- 480 DPI（每英寸点数）标题轮直接渲染页面上部 55% 区域并保留边缘护栏，最终送入 OCR（文字识别）的像素与旧整页渲染后裁剪完全一致；直接裁剪异常时自动回退旧路径
- 整份文件完全没有识别出页段边界时，后备分类先使用 300 DPI（每英寸点数），必要时再使用 480 DPI（每英寸点数）复核第一页
- 多个强正文组合无法确定唯一类型时标记为分类冲突；保密协议标题漏识别时可结合甲乙方、保密内容、商业秘密及达成协议等结构确认；文字层和两次图片识别均缺少足够有效文字时也标记为不确定页，防止该页静默并入上一档案
- 多页文件没有识别出任何可靠页段边界时，无论整文件后备结果来自文件名、文字层还是图片识别，均拒绝自动归档；分析服务返回具体页码、候选类型或原因，整份文件不拆分、不落库
- 类型顺序不固定；缺失类型不生成记录，同一类后续无标题页面沿用当前类型；同类型首页被其他档案分隔后会新建页段，不跨越中间材料合并
- 明确离职证明、职业资格材料属于强“其他”边界；通用标题属于弱证据，整页与标题区两路识别一致后才可作为“其他”边界，并排除“成如下协议”“达成如下协议”“签订本协议”等正文句。单独上传、内容可读且无法匹配固定十类的单页文件仍归入“其他”；多页文件没有可靠页段边界或页面缺少有效识别文字时需人工核对
- 同一整册出现多份额外材料时按各自边界分别拆分，数据库类型统一为“其他”，展示文件名保留识别到的资料名称
- 图片识别和拆分临时文件在处理后清理；分类过程不记录档案正文，避免身份证、银行卡和合同内容进入服务器日志
- 生产反向代理仅对员工人事档案自动识别上传接口设置 40 分钟读取和发送等待上限，与浏览器端保持一致；生产更新会主动校验、重载并复核 Nginx（反向代理）运行配置，其他接口继续使用默认超时

### 9. 劳动合同期限与工资同步

- [server/services/employmentContractOcr.ts](../server/services/employmentContractOcr.ts) 优先读取劳动合同前四页文字层，扫描件按第二页、第一页、第三页、第四页顺序执行 OCR（文字识别）
- 合并档案分类阶段的候选文字按原页码映射到拆分文件后复用于邀请函薪酬和劳动合同期限解析；始终先读取准确文字层，多个图片候选必须全部解析成功且字段一致才复用，否则完整保留原 300/600 DPI（每英寸点数）回退，OCR（文字识别）原文不进入接口响应或数据库
- 在“劳动合同期限”条款内提取起止日期；同时存在试用期时选择跨度最长的正式合同期限，并兼容扫描日期中的下划线及常见误识别
- 同步解析每份合同“试用期”条款中的截止日期；续签合同试用期栏位为空时返回空值
- 合同归档后以第一份已识别合同维护员工入职日期和试用期截止，以结束日期最晚的一份维护当前合同；续签不会覆盖入职或试用期日期
- 没有合同或合同期限识别失败时不使用账号创建时间、手填日期或固定月份推算，员工入职日期保持为空
- [server/services/payrollRecordSync.ts](../server/services/payrollRecordSync.ts) 统一同步当前及未来月份工资；涨薪起算日优先使用最早一份已识别合同的开始日期，没有合同数据时才回退入职日期
- 工资同步服务联查账号角色，BOSS、董事长和超级管理员不生成或更新工资记录
- 正式邀请函上传会重置本月工资手工标记；合同新增、删除触发的自动重算保留管理员手工工资、缴费基数和个税

### 9.1 人力成本银行回单与个税明细识别

- [server/services/humanCostReceiptOcr.ts](../server/services/humanCostReceiptOcr.ts) 复用银行回单金额识别底座，独立处理人力成本文件，不写入报销回单批次或待认领数据
- 图片文件直接执行 OCR（文字识别）；PDF（便携式文档格式）先按页转换为图片，并复用工行同页上下两笔回单的结构分析和切分能力
- 每一笔候选回单均调用财务区审批中心相同的付款回单解析和真实性校验，缺少银行、回单、金额、收款人、账号或银行特征字段时不进入汇总；公积金、社保和税务回单允许机构全称作为收款人，OCR（文字识别）偶尔漏掉第二个“户名”标签时仍可从“住房公积金管理中心”等机构名称兜底提取
- 实发工资额外校验摘要、用途、备注或客户附言中的工资语义；一个 PDF（便携式文档格式）中的非工资回单会被明确忽略，不计入失败笔数
- 实发工资在至少识别出一笔有效工资回单后直接返回已识别，不再因同一文件的其他失败片段进入待核对；工资语义判断先于银行回单字段校验，避免无关内容产生误报
- 通过校验的工资回单返回收款人、收款账号、金额、电子回单号、页码和上下位置；业务路由优先按完整账号、其次按户名精确匹配员工，同名时保持待核对
- 多笔金额先转为整数分再求和，避免 JavaScript（脚本语言）浮点误差；全部、部分和全部失败分别返回 `recognized`、`partial`、`failed`
- 识别用临时图片在处理结束后立即清理，数据库不保存 OCR（文字识别）全文；单笔工资关联仅保存预览定位所需字段
- 所有回单识别任务通过进程内去重串行队列执行，避免页面轮询把同一历史回单重复提交；任务异常后短暂熔断后续识别，不阻塞登录和普通接口
- 实发工资回单先确认摘要、用途、备注或客户附言中的工资语义，再复用银行、回单、金额和交易凭证真实性校验；收款账号偶发漏识别时允许保留已识别的收款户名，并由工资关联层按姓名精确匹配员工，其他回单仍要求账号完整
- OCR（文字识别）常驻子进程超时或服务关闭时使用强制终止；串行队列会等待旧子进程的 `exit（退出事件）` 或 `close（关闭事件）` 完成，确认旧模型释放后才允许后续任务启动，避免多个模型同时占用资源
- [server/services/payrollTaxDetailOcr.ts](../server/services/payrollTaxDetailOcr.ts) 复用同一 OCR（文字识别）常驻进程的文字框坐标；先定位“应纳个税”表头的真实横坐标，再按工资表中的员工姓名逐行提取交叉单元格
- “住房公积金 应纳个税”等合并识别表头按字符比例还原“应纳个税”中心位置；员工行在该列没有文字框时按空白单元格填 0，列内有无法解析文字时不误填并返回未识别名单
- PDF（便携式文档格式）个税明细先逐页转换为图片，最多支持 30 页；同一员工重复出现且金额不一致时拒绝批量回填，避免覆盖为不确定结果

### 9.2 审批中心整包银行回单原子持久化

- [server/services/bankReceiptProcessor.ts](../server/services/bankReceiptProcessor.ts) 把整包 PDF（便携式文档格式）拆为单张回单后处理；自动匹配与 [server/routes/bank-receipts.ts](../server/routes/bank-receipts.ts) 的手工认领共同调用 `persistBankReceiptTransaction`，每张回单使用一个独立数据库 `transaction（事务）`，避免整包长事务及单张失败污染其他回单。
- 持久化前必须得到唯一且合法的银行实际交易日期；回单金额、报销净额、付款批次总额和明细快照统一转成整数分比较。收款校验同时要求申请人档案与回单双方都有姓名和完整账号，并分别精确匹配，不能只凭姓名或账号尾号通过。
- 服务以回单裁片 SHA-256（安全散列算法）摘要和规范化电子回单号双重防重。无付款批次的报销单必须已处于 `paid（已确认付款）`，服务自动创建 `uploaded（已上传回单）` 批次和明细；已有唯一 `pending（待处理）` 批次时兼容成员仍为 `approved（已审批）` 或已转 `paid（已确认付款）`，但必须复验同一收款人、完整成员集合、批次快照和整数分总额。
- 匹配成功会原子写入或更新回单、批次、批次明细、报销状态、防重记录和审批记录。自动候选的业务校验失败时先完整回滚，再用同一识别证据原子保存为 `unmatched（待认领）`；数据库或文件基础设施异常继续报错，不降级成待认领。
- 手工认领模式不接受客户端回传 OCR（文字识别）字段；服务在事务内锁定既有待认领回单，并从数据库保存的权威证据恢复完整账号、电子回单号和唯一交易日期。历史证据不完整或裁片丢失时失败关闭，要求重新上传清晰原件。
- 匹配完成后统一进入付款批次闭环；申请人通过批次确认收款，同批报销单和批次状态在一个事务内完成。

### 10. 入职模板员工编号、合同日期与职位写入

- [server/services/onboardingTemplateNumber.ts](../server/services/onboardingTemplateNumber.ts) 使用 `pdftohtml（PDF 文字坐标提取工具）` 逐页读取文字、坐标和字体颜色，再使用 `pdf-lib（PDF 处理库）` 写入当前员工编号
- 入职邀请函处理全部页面；劳动合同书第 1 页处理右上角黑色编号，第 2 页起处理左上角蓝色“合同编号”；新员工入职申请表只处理第 1 页
- 劳动合同书额外定位“劳动合同期限”和“试用期”行中的年月日空位，按员工模板拟定日期分别写入合同起止和可选试用期起止日期
- 劳动合同书识别第二页第四条“担任……岗位”中的示例职位区域，向左扩展覆盖示例文字的抗锯齿边缘后写入员工当前职位，并保留完整的“担任”、下划线和前后正文
- 自动写入的数字使用相邻“年、月、日”文字的实际字号，并向上调整基线，与正文大小一致且不贴近模板下划线
- 离职模板首先使用系统文字定位工具读取字段，异常 PDF（便携式文档格式）自动回退到 PDF.js（PDF 解析器）；编号基于每页原完整编号的真实字形框覆盖，不复用其他页面坐标
- 中文职位通过高分辨率透明图层写入，使用容器内置中文字体并按职位空位自动缩放；下划线保持与相邻汉字基线对齐，通过上移自动职位文字留出清晰间距
- [server/services/contractTemplateCycle.ts](../server/services/contractTemplateCycle.ts) 在正式劳动合同归档事务中清空四个新周期拟定日期；下载随即锁定，预览保留最新版模板的空白日期，第四条岗位仍使用员工当前职位
- 三类模板上传时逐页试写示例编号；劳动合同书同时试写示例日期和职位，缺少目标位置、文件加密或页面旋转异常时直接拒绝保存
- 自动写入编号只用于员工下载入职模板；管理员上传至 `employee_documents` 的历史或正式人事档案不调用本服务
- 管理员预览模板时返回原模板，员工下载时生成带当前编号和拟定日期的临时副本；原模板和管理员上传的人事档案内容、编号及文件名均不改写
- 员工编号由 ASCII（美国信息交换标准代码）字符组成，使用内置无衬线字体写入，不需要加载中文字体

### 10.1 离职档案识别与模板处理

- [server/services/resignationDocumentClassifier.ts](../server/services/resignationDocumentClassifier.ts) 逐页识别五类离职档案首页，优先读取文字层，扫描件回退至共用 PaddleOCR（飞桨文字识别）进程；标题按中文主体归一化匹配，兼容全角或半角分隔符、空格、标题前置填充文字及少量识别误差

### 12. 合同识别、核算与盖章核验服务

#### 草拟合同识别

- [server/services/contractOcr.ts](../server/services/contractOcr.ts) 负责甲方、乙方、项目名称、合同金额、合同类型和合同签订日期六个核心字段的候选提取；每个字段返回原始值、规范值、最终候选、未舍入最终验证值、来源页码、独立证据和冲突警告；
- 资产类房屋租赁合同使用专用金额规则：只读取租赁合同正文，明确排除收据、押金、保证金、定金、首期／分期付款、银行回单、水电燃气热力费、公共区域维修更新改造及临时一次性费用；正文明确包含全部固定费用的综合总金额时优先采用，否则同时识别月租金和具有明确月度固定语义的物业管理费，按两项之和乘租赁月数计算；仅有月租金时继续按月租金乘租赁月数，期限缺失时按十二个月计算。同时识别租赁开始日、到期日、月物业管理费，保留“正文总额／月租金计算／月租金与月物业费计算”来源。普通服务费、维修费或按实际发生的物业相关费用不得自动纳入。
- 扫描合同首页的“项目名称”因表格换行、印章或裁片被截断时，系统可使用正文“甲方委托乙方就……项目进行专项服务”的闭合句恢复完整名称；只有同一完整值至少获得两档可见 OCR（光学字符识别）结果复核，且候选排序不存在真实冲突时，正文证据才可补强首页分行字段。单次正文命中、普通服务描述或不同项目名称仍保持阻断；
- PaddleOCR（飞桨文字识别）与 PaddlePaddle（飞桨深度学习平台）分别固定为 3.5.0 和 3.2.2，不升级运行环境。`OCR_MODEL`（识别模型配置）支持 `v4_mobile`（第四版移动模型）、`v5_server`（第五版服务器模型）与 `v6_medium`（第六版中型候选模型）；开发容器默认第六版，生产容器及无显式环境变量的运行时安全回退仍默认第四版。常驻进程切换模型前释放旧实例，三套模型不同时驻留。第五版服务器模型在 CPU（中央处理器）推理时独立关闭 MKLDNN（英特尔深度学习加速库）、使用单处理线程并将检测长边限制为 640 像素，避免默认 960 像素检测张量触发 OOMKilled（内存耗尽终止）；第四版移动模型继续保持原有加速参数；
- `v6_medium`（第六版中型候选模型）读取 [server/config/ocr-v6-medium.json](../server/config/ocr-v6-medium.json)，使用官方 `PP-OCRv6_medium_det`（第六版中型检测模型）和 `PP-OCRv6_medium_rec`（第六版中型识别模型）参数。镜像构建通过 [server/scripts/prepare_ocr_v6_medium_models.py](../server/scripts/prepare_ocr_v6_medium_models.py) 校验两份官方模型的 SHA-256（安全散列算法），并准备到只读持久模型目录；PaddleOCR（飞桨文字识别）仍严格固定为 3.5.0。模型目录缺失时明确失败，禁止回退到其他模型或运行时在线下载。现有双模型对比接口仍固定 `v4_mobile` 与 `v5_server`，默认生产模型仍为 `v4_mobile`；
- [server/scripts/evaluate-contract-ocr-models.ts](../server/scripts/evaluate-contract-ocr-models.ts) 是不写数据库的离线评测脚本，可对同一绝对路径样本清单串行执行三套模型，固定使用原 PDF（便携式文档格式）、页面范围、DPI（每英寸点数）、裁片、日期增强和字段解析规则，并输出总耗时、字符数、识别行数、平均原始置信度、五项字段结果与诊断分、候选冲突数量。该脚本不注册路由，也不进入合同任务队列；
- DOCX（开放 XML 文字处理文档）读取压缩包内的当前可见正文和表格文本；真实 DOC（旧版 Word 二进制文档）经 OLE（复合文档）结构校验后，在隔离临时目录串行转换为 DOCX 再读取。PDF（便携式文档格式）可先提取电子文字层提出候选，但无论六项是否齐全，都必须继续渲染包含字段证据的可见页面并调用本地 PaddleOCR（飞桨文字识别）；合同正文不发送外部服务；
- DOCX（开放 XML 文字处理文档）正文提取将内部 `word/embeddings`（嵌入对象目录）及其 `OLE Package`（OLE 通用包）作为不透明静态内容忽略，不打开或执行嵌入载荷，也不因目录项本身误报活动对象；同时排除显式 `vanish`（隐藏文字属性）／`webHidden`（网页隐藏属性）运行、删除修订、移动前内容及域指令文字。样式表出现启用的隐藏属性时不模拟不完整的 Word（文字处理软件）样式级联，而是安全失败。`vbaProject`（宏工程文件）、`macroEnabled`（宏启用内容类型）、`word/activeX`（活动控件目录）以及指向外部的 `attachedTemplate`（附加模板）、`oleObject`（OLE 对象）和 `package`（通用包）关系继续拒绝；
- PDF（便携式文档格式）扫描页先按 300 DPI（每英寸点数）识别，弱字段再使用高清档复核；高清页只沿阅读方向纵向切成带重叠的安全裁片，每片不超过 200 万像素且最长边不超过 4000 像素，按原页顺序合并并消除切缝重复行。标准 A4（国际标准纸张）300 DPI 页面预先拆为六个纵向裁片；最大 4000×8000 像素页面最多拆为 32 片，同页始终保留完整行宽，不横向切断字段名和值。直接上传的 JPG（联合图像专家组格式）或 PNG（便携式网络图形）合同图片同样先等比例缩至安全画布，再沿纵向套用相同裁片规则，禁止整张超限图片直接送入识别引擎；同页按最终实际渲染分辨率去重，既保留小字清晰度，又降低检测张量内存峰值；
- 合同识别进程内所有 `pdftoppm`（PDF 页面渲染命令）共用容量为 1 的渲染信号量，高分辨率页面只能依次渲染。PaddleOCR（飞桨文字识别）关闭合同 PDF（便携式文档格式）不需要的行方向模型，每个裁片完成后执行对象回收和空闲堆页释放，避免连续页面造成 OOM（内存耗尽）；
- 合同六字段与盖章合同核验统一只调用 PaddleOCR（飞桨文字识别），不再调用 Tesseract（开源文字识别）。解析器内部将 `ocrConfidence`（识别原始置信度）与 `fieldScore`（字段规则评分）分开保存：前者保留 0 至 1 的模型原值，非 OCR 来源为 `null`（空值）；后者保留锚点、候选一致性和独立证据形成的 0 至 100 整数规则分。现有数据库及接口中的 `confidence`（兼容评分字段）继续等于 `fieldScore`，不改变字段结构。自动采用策略不读取精确 100 门槛，也不改写两类分数；OCR（光学字符识别）服务完成字段专属二次排序后，以进程内 `WeakMap`（弱映射）安全上下文校验项目候选来源、语义和分差，以及金额角色、作用域和冲突状态，再执行甲乙方、分类／层级、日期及上下级上下文硬业务校验；
- 项目候选冲突、金额角色冲突或日期证据偏弱时，合同识别服务自动定位相应锚点区域，使用同一模型执行灰度归一化、锐化和日期二值化局部复识，再重新生成和排序目标字段候选。PDF（便携式文档格式）日期专用增强与通用风险复核共享每份文档最多六个区域的预算，并按页码、DPI（每英寸点数）和坐标去重；图片合同使用原图坐标执行同类局部增强。增强裁片的完整逐行结果、页面坐标、原始置信度和模型版本继续保存，内部 `fieldScope`（字段作用域）确保增强文字只参与触发字段，不能污染其他字段；
- [server/services/tesseractOcrDaemon.ts](../server/services/tesseractOcrDaemon.ts) 仍提供完全离线的 Tesseract（开源文字识别）基础能力，只供仍明确配置该引擎的其他流程兼容使用；它不参与合同六字段、盖章合同或银行回单的候选、诊断分、方向判断和自动采用决定；
- PDF（便携式文档格式）电子文字层与可见页面图像候选继续分别保留来源、页码和冲突证据；DOC 与 DOCX（文档格式）当前未执行可靠可见渲染比对，结构化正文单独最高 99。上述分值与证据继续用于候选排序和诊断，但任务不再仅因单通道、低于 100 或二次排序后的冲突警告进入 `partial`（部分结果）；
- 项目名称候选排除“合同类型、服务内容、签订日期、合同生效时间、付款方式、甲乙方”等元数据行，并结合首页标题位置、合同语义和反例降权。从项目名称、工程名称、合同名称或首页标题开始最多读取后续四个有效行；除空值、括号未闭合和连接符外，“施／工许可证”“创新园／110 千伏”等具有明确项目形态的无标点断行也可安全拼接。独立且唯一的“项目：”为最高权威字段，“项目名称：／项目全称：”为次级权威字段；权威字段存在完整闭合值时，首页合同标题、公司抬头、正文委托句和服务范围只保留为旁路证据，不得覆盖或追加“前期手续／项目”等文字。若同级权威字段出现两个不同值则继续保留冲突，不擅自选择。明确“项目名称／工程名称／信息咨询项目名称”等字段标签后的完整值按项目字段本身保留，属于名称正文的“咨询服务／技术服务”尾词不再被通用合同类型清洗截掉；只有后续独立“合同”行与尾词共同组成文档类型时才剥离。遇到甲方、乙方、委托方、受托方、发包方、承包方、合同金额、日期或编号立即停止；供电公司抬头、孤立残片和已识别主体单位不得进入最终项目名。“甲方委托乙方就……项目进行”的正文明确描述可补全被首页版面错序截断的标题。甲乙方优先读取明确甲方／乙方标签紧随其后的单位全称，仅无明确标签时才采用委托方、受托方等通用角色候选，多个明确标签冲突时继续阻断；
- 明确“项目名称：／项目全称：”字段的首段以项目、工程、变电站、线路或电缆隧道等强项目主体闭合时，紧邻同页且完整匹配“前期手续技术咨询服务／前期手续咨询服务／前期手续技术服务／前期手续办理”的下一有效行仍属于同一字段。系统合并两行原文证据并保留业务服务尾词；该窄规则不适用于“服务内容：”标签、普通正文句、非闭合前期描述、下一页或后续主体／金额／日期字段；

- [server/services/contractSealApplication.ts](../server/services/contractSealApplication.ts) 将当前合同快照、页面编辑字段和合同创建人个人签名生成合同用印申请 PDF（便携式文档格式）。客户端只能提交表单字段；服务端先核验当前操作人就是合同创建人，再在签署事务中重新读取该账号的 `user_signatures`（用户签名），规范化签名图片并复制本次签名快照；生成的单页申请单在申请人和总经理签署区只显示姓名和职位，不显示部门。内部签署快照仍保留姓名、角色、部门、职位和时间用于追溯，不信任前端签名图片；提交审批还会再次核验签名人编号与合同创建人编号一致；
- 用印总份数由独立纯解析服务从当前草拟合同识别原文的唯一“一式×份”提取，并以甲乙方明确持有份数作为最低一致性校验；支持阿拉伯数字、中文数字、财务大写和表单下划线分隔。未签申请只返回识别事实，不能回退历史草稿或默认数值；已签申请继续读取签署时固化的可信快照。读取失败返回 `null`（空值）及明确未识别状态，保存和签署仍失败关闭；
- 已签名用印申请绑定 `contracts.version`（合同版本）。合同主数据后续变化时，提交审批安全失败并要求重新签名；同合同新申请会把旧申请标记为已替代，历史文件和签名快照保留用于审计；
- 申请人生成的用印申请 PDF（便携式文档格式）固定为一页 A4（国际标准纸张），底部同时显示申请人签字区和预留的总经理审批签字区，并写入固定单页版式标记。总经理通过首次用印审批时，同一服务重新读取总经理本人当前活动账号和锁定电子签名，校验申请人原 PDF（便携式文档格式）受控路径、SHA-256（安全散列算法）摘要、版式标记、单页尺寸及零旋转后，只在同页预留区写入总经理姓名、审批时间和签名，不追加页面。旧版或版式异常申请单安全拒绝补签；一页双签文件成为唯一用印申请附件，数据库旧附件记录随审批事务删除，事务提交后再删除申请人单签物理文件。审批事务失败时数据库删除自动回滚，并只清理本次新生成的 PDF（便携式文档格式）和总经理签名快照，不误删申请人原件。项目负责人审批、驳回、评论、解除协议审批和盖章差异复审不执行该签名流程。

#### 辅助材料档案与核算隔离

- [server/services/contractAuxiliaryPackage.ts](../server/services/contractAuxiliaryPackage.ts) 只允许为 `requires_auxiliary_materials = TRUE` 的合同新增档案；创建页和详情页负责开关，台账按开关显示“添加辅助材料”并导航至合同详情独立页签挂载档案组件，不使用弹窗。首次建档必须上传至少一份辅助合同；已有档案后可向最新档案只追加发票或回单，无需重复上传合同。辅助合同、发票和回单三类均可多份，合计最多 20 份、单份最多 30MB，并可填写特殊情况备注；同包跨批次相同文件摘要固定拒绝；
- 辅助档案的 `accountingIncluded`（纳入核算）在类型、服务、路由和数据库四层均固定为否。客户端尝试伪造开关时拒绝，正式合同金额、项目总额、发票、回款、付款和经营统计都不读取辅助档案表；
- 创建使用短事务保存档案包和全部文件；任一文件的真实格式、结构、扩展名、大小、受控路径或摘要校验失败时整批拒绝并清理本批临时文件。校验通过后直接标记为已归档，不调用合同 OCR（光学字符识别）、不生成甲乙方或金额结果，也不提供重新识别入口。版本化备注、带审计删除和鉴权预览继续保留；详情和列表按文件类型、创建时间、文件编号稳定返回同类多附件。服务启动时将历史遗留的处理中辅助档案转换为已归档且不触发识别。公开响应使用脱敏 DTO（数据传输对象），不返回服务器存储路径、文件摘要、完整原文、坐标或内部操作人编号。

#### 异步识别队列与租约

- 合同草拟识别使用进程内有界调度队列，`CONTRACT_OCR_CONCURRENCY`（合同识别并发配置）限制为 1 至 4，默认 2，避免多份扫描合同同时占满本地识别资源；
- 每个 PDF（便携式文档格式）页面的普通非基础设施异常在同一任务内先按原参数自动补扫，再提高分辨率补扫；用印份数页面还会按“一式／各执／同等法律效力”锚点执行独立高清复核，无锚点时覆盖正文末四页。基础设施、内存或进程错误不循环重试；自动补扫后仍缺页或未形成唯一总份数时不能把整单保存为成功；
- 数据库任务通过 `worker_token`（工作实例令牌）原子认领，并写入 5 分钟 `lease_expires_at`（租约到期时间）；执行期间每 60 秒续租；
- 只有仍持有当前工作实例令牌、且文件仍为当前草拟版本的任务才能提交结果。旧实例晚到结果、已替换文件和重复认领任务均不能覆盖新数据；
- 服务启动时恢复排队任务，此后每 60 秒检查一次租约过期的执行任务并重新排队，同时接管“任务已写入但服务立即退出”的极小时间窗口；
- 排队或执行中的任务禁止重复提交。未达到自动采用标准或失败的任务可显式对整份当前文件重试；页面轮询结束或离开不会删除草稿、原文件和已形成的证据。只有最新 `partial`（部分结果）任务在停止识别后开放财务整组确认，排队、执行、失败或已被替代任务均不能确认。

#### 合同领域与核算服务

- [server/services/contractService.ts](../server/services/contractService.ts) 统一校验包含 `rejected`（已拒绝）的八态生命周期、四类合同关系、上传锁定行政区、预选大类和二级分类、同区项目归属、二级协议上级合同、必需附件、金额边界、审批资格、草稿删除／撤回、盖章前撤销和财务三态；盖章前撤销采用软删除并检查盖章文件与核验记录，审批中的合同同步关闭待处理轮次，文件和历史证据不删除；主合同、独立合同固定为一级并强制无上级、以自身为根；二级分类属于用户上传前锁定业务值，识别只核对合同大类，不依据不充分原文自动改写；
- 项目归属不是提交审批的必填项，也不再参与审批人解析。主营、非主营、资产类及其协议的业务审批统一锁定唯一活动总经理；管理员只负责上传、提交、维护和盖章归档，项目负责人及普通员工不生成审批节点。服务启动把历史未处理项目负责人轮次重指向唯一活动总经理并保存迁移审计；活动总经理缺失或不唯一时明确阻断；
- 草稿更新路由自身拒绝任何上传后的 `relationType`（合同关系）输入；前端更新类型与构建载荷已移除 `parentContractId`（上级合同编号），上传识别元数据继续携带。请求只要出现该字段，即使值与当前上级相同或为 `null`（空值），也立即返回 `409 CONTRACT_PARENT_IMMUTABLE`（上级合同不可修改）且不进入领域服务。领域服务在合同行锁内再次拒绝实际上级变更，避免内部调用绕过路由；主合同、独立合同始终无上级，补充协议、终止协议始终沿用上传时锁定的一级合同；恢复草稿与候选加载失败时保留锁定编号并只读展示；
- 盖章版识别先校验待盖章状态及版本，并读取审批合同已经锁定的合同分类与合同关系，再携带该上下文进入独立有界队列；上传与重新识别使用同一路径。资产类房屋租赁盖章版继续生成租赁专用合同总额候选：综合总额优先，否则固定月租金与明确月物业管理费合计乘租期，仅有月租金时按原公式；收据、保证金、首期／分期款、水电能源和维修改造费用继续排除，不能退回无分类的通用金额猜测。并发和等待上限均可配置，队列满时快速失败，重试完成后仍在事务内复核版本；
- 合同草稿软删除会取消识别任务；未消费的临时财务上传在用户移除或清空时硬删除原件、附件索引、全局摘要与识别任务。未确认财务登记草稿按登记编号整组硬删除发票／回款／付款事实及其上传证据，释放摘要后允许同一文件重新上传；审计只记录删除人、业务编号与动作。已确认、已冲正和已进入核算的数据继续完整保留，没有登记编号的历史单条草稿兼容同一草稿硬删除边界；
- 数据库序列按上海日期生成 `HT-YYYYMMDD-######` 系统内部流水号。主营业务中的每一份文件可拥有独立原件业务编号；识别服务优先解码二维码并完整保留补充协议 `(B1)`、解除协议 `(C)` 等自身后缀。补充协议可由 `(B数字)` 反推基础原合同编号，解除协议可由 `(C)` 反推；明确“原合同编号／主合同编号”存在时优先采用明文核对锁定目标。自身编号独立查重，基础编号只核对关系，两者不得互相覆盖。主合同金额为正，补充协议使用有符号调整额；解除协议由结算快照生成小于或等于 0 的调整额；
- 项目元数据接口同时返回 `worklog_projects.district`（项目行政区）。上传成功后合同 `area` 锁定，项目候选只返回同区记录；项目归属服务于项目金额累计和经营统计，不等于合同层级关联。主合同和独立合同不查询上级候选，只有补充协议和终止协议在上传前查询同区且分类、资产子类一致的有效一级合同并锁定选择。草稿保存时只重新校验可修改的项目关系；上级合同不再属于更新输入，客户端伪造或内部调用尝试改写时拒绝，不得用项目或上级合同覆盖合同 `area`、`declared_category`、OCR（光学字符识别）`category` 或资产子类；
- 合同提交、审批、解除归档、项目金额同步和审计记录使用 PostgreSQL（关系数据库）事务、行锁和根合同组咨询锁，避免协议并发归档后金额错误。解除协议审批及待盖章阶段只冻结结算快照和新增财务记录，不修改目标状态；盖章归档时重新计算并核对快照，原子终止目标及更新根合同金额；
- 新财务登记可先消费至少一个已验证发票任务，形成不可确认、不可核算的待回款发票草稿，也可同时保存已到账但尚未覆盖全部发票金额的银行凭证。后续可在同一登记多次补充回款／付款，支持多对一、一对多和多对多；服务端以整数分校验累计结算不得超过累计发票，并在同一事务中创建银行事实与部分对应关系。每批银行凭证保存后立即确认并参与已收／已付、完成率及经营核算，发票金额不重复计入收入；
- 服务端优先匹配金额完全相同的凭证，剩余金额再按上传顺序逐笔分配，生成“发票—回款／付款回单—对应金额”明细；每次保存必须完整分配本批银行凭证，允许保留未结发票余额。确认事务再次锁定全部明细和对应关系，只有发票合计、结算合计和对应分配合计三者按分一致才可确认；
- 发票以 NFKC（兼容等价规范化）后的销售方名称和发票号码防重；全部财务原件按 SHA-256（安全散列算法）跨合同全局防重。发票识别任务完成写入前就取得业务键咨询锁，同时查询既有发票事实与已验证未消费任务；不同文件摘要但同销售方、同发票号码的文件也会在上传阶段被隔离。草稿、已确认和已冲正发票均永久占用业务键；多发票批次按业务键字典序取锁，数据库唯一索引冲突统一返回 `DUPLICATE_CONTRACT_INVOICE`（合同发票重复）。银行回单在识别完成写入前以规范化电子回单号码取得全局咨询锁，并查询已验证／已阻断未消费任务及历史收付款事实；相同号码立即隔离，登记保存再次使用同一号码锁复核。付款时间、金额、付款／收款人及双方账号不参与查重键；
- 标准电子发票 PDF（便携式文档格式）按“项目名称／金额／税额”坐标列逐行解析，项目名称列续行在下一金额行前拼接；税收分类前缀只作原文保留，成本分类读取前缀后的业务名称。每条含税金额按整数分由不含税金额加税额生成，逐条合计必须等于价税合计；资产房屋租赁合同缺少可靠明细时禁止回退到整票分类或静默归入其他成本。已确认付款按发票与回单既有分配额再按明细含税占比分摊，最后一条承接尾差，冲正后查询自动排除；
- 上述逐条坐标拆分和成本分类仅在服务端收到资产房屋租赁上下文时执行；非租赁资产与收入合同跳过明细分类并保持原整票识别安全门禁，避免把业务支出误套入租赁分类体系；
- [server/services/invoiceCrossModuleDeduplication.ts](../server/services/invoiceCrossModuleDeduplication.ts) 为报销真实发票、报销核减发票和合同财务发票提供共享号码规范化、跨模块占用查询和事务级咨询锁。报销批量创建／编辑、恢复和核减写入与合同识别结果写入都在同一 `global-invoice-number`（全局发票号码）锁命名空间中按字典序执行，避免反序批次死锁或两模块并发双写。报销的无票收据以 `receipt-`（收据文件前缀）或 `RECEIPT-`（收据号码前缀）明确排除，不会占用发票号码；
- 资产付款使用房租、电费、车位费、租车、网费、其他六类，主营商务费用率为 10%。

- [server/services/contractAccounting.ts](../server/services/contractAccounting.ts) 将金额转换为整数分、费率转换为基点后逐项计算，避免 JavaScript（脚本语言）二进制浮点误差；
- 主营核算依次计算 11.72% 税费、税后 5% 预扣营销、扣除前两项后 10% 商务费用；非主营计算 0.28% 财务成本和 11.72% 税费；
- 回款被确认时冻结该业务日期对应的费率快照；经营统计优先使用记录快照，历史记录没有快照时才按费率版本区间回退，新增未来费率不会反向改写既有核算结果。

#### 月度银行回单识别与业务证据链接

- [server/services/monthlyFinancialBankStatement.ts](../server/services/monthlyFinancialBankStatement.ts) 处理基本、一般、商务账户整月 PDF（便携式文档）：结构化商务账户按文字层中的多组回单编号拆分，扫描版一般／基本账户按视觉空白检测和中线裁片拆分；一张页面可产生上、下两笔，纯白页面直接跳过；
- 账户只按完整账号 `0200049609201258271`、`0200303519000018418`、`321240100100245908` 精确识别，账号按文本保留前导零。文件名仅提示可能账户；文件名与正文冲突时采用正文并生成异常。归月只读取银行“交易日期／时间戳”，不采用打印日期、记账日期、起息日、文件夹或备注月份；

- [server/services/monthlyFinancialBankLinker.ts](../server/services/monthlyFinancialBankLinker.ts) 在同一 PostgreSQL（关系数据库）事务内按规范化电子回单号查找旧业务凭证。主营收入和资产支出只有电子回单号、双方完整账号、银行交易日期、金额、确认状态和合同分类全部一致时，才生成有效展示替换及分类依据链接并允许月报接管；没有记录或任一条件不符时仅将该笔银行交易转为待关联并排除合同金额，不再回滚整批。部分文件只让识别确定的一般／商务利息和跨行手续费进入月报，其他业务继续使用旧来源；原合同、报销、薪资记录和金额从不修改或删除；

- 页面识别失败、同页多回单未可靠拆分、同一文件回单号对应内容冲突或任一交易待复核时，服务在持久化前拒绝候选文件，旧活动文件和月报快照保持不变。已有活动文件为历史部分识别或仍存在待复核交易时，月结返回 `MONTHLY_BANK_REVIEW_REQUIRED` 并禁止生成不可变快照。
- 合同收付款冲正会同步停用月底银行证据链接，将交易和活动文件转为待复核；开放报表查询实时合并该状态并禁用月结按钮。月结事务中的多来源查询按单连接串行执行，事务外才并行查询，避免数据库驱动并发复用同一连接。上传文件名先完成中文字符集还原、安全基名截取和长度限制，再进入账户提示识别及持久化。

- [server/services/monthlyFinancialReimbursementMatcher.ts](../server/services/monthlyFinancialReimbursementMatcher.ts) 接收月报现有 PostgreSQL（关系数据库）连接，在全部银行交易及员工分类完成后执行两阶段唯一匹配。服务支持单回单对应单报销、同日多回单合计对应单报销、单回单对应同类型多报销；歧义保持员工已匹配和报销待关联。唯一匹配时原子创建或更新付款批次、明细、防重身份、报销状态、审批记录及具体报销／批次展示链接；既有回单只在规范回单号、付款批次、成员和总额全部一致时替换当前裁片与业务日期，并保留完成状态、确认人与旧证据。

- [server/utils/payment-proof-identity.ts](../server/utils/payment-proof-identity.ts) 为月报、审批中心单笔／批量及整包回单提供统一回单号、文件摘要、事务锁和数据库查重。所有调用方先锁凭证身份，再锁报销、付款批次和明细；相同回单号的并发路径只有一个能够提交，另一路在条件更新或唯一约束处返回状态冲突。月报换版额外校验旧、新业务日期均属于报表月，同一交易存在多个历史批次归属时不执行替换。
- 上传结果不确定时，浏览器支持摘要接口则保存本批 SHA-256（安全散列算法）摘要并与服务端本月全部历史摘要核对；局域网 HTTP（超文本传输协议）环境无法生成本地摘要时不阻断上传，改为保存文件显示信息，刷新后由管理员触发安全重试，服务端以文件摘要、电子回单号和月报版本权威防重。确认前禁止切换月份或离页，页面不会自动重发。月结快照预览地址携带当时文件编号，后续整包换版仍读取旧裁片。数据库提交响应不确定时保留稳定原件，不按普通失败清理。

#### 合同财务凭证识别底座

- [server/services/contractFinancialOcr.ts](../server/services/contractFinancialOcr.ts) 提供单份和串行批量两种独立调用方式，统一识别发票与银行回单，并已接入合同财务上传路由、任务存储和详情页；选择文件后立即由服务端识别，客户端不参与生成识别字段；
- [server/services/contractFinancialWorkflow.ts](../server/services/contractFinancialWorkflow.ts) 在凭证真实性验证之上执行合同业务方向门禁：主营／非主营发票只接受销项、回款只接受收款，资产发票只接受进项、付款凭证只接受付款；同时将旧客户端字段降为只读一致性断言，任何改写均拒绝；
- 发票支持真实 PDF（便携式文档格式）、JPG（联合图像专家组格式）和 PNG（便携式网络图形），业务快照和页面只输出购买方名称、销售方名称、开票名称、发票号码、开票日期、税费、开票金额七项。开票名称按票面“项目名称”列的坐标边界提取，保留 `*生产生活服务*` 等税收分类前缀、明细名称和项目续行，多个项目使用顿号连接；“规格型号”列及其右侧的单位、数量、单价、金额和税额永不拼入开票名称。双方纳税人识别号、正文状态和进项／销项／第三方方向只在服务端参与主体及凭证安全校验；兼容左右并列、竖排标签及老式增值税发票按坐标分栏的名称、税号、开票名称和税额版式；
- 银行回单支持真实 JPG（联合图像专家组格式）、PNG（便携式网络图形）和 PDF（便携式文档格式），新合同财务流程只输出电子回单号码、付款时间、付款人户名、付款账号、收款人户名、收款账号、金额七项。付款时间依次读取“付款时间／交易日期时间／交易时间／交易日期／转账时间／转账日期／时间戳”，统一规范化为 `YYYY-MM-DD`，原件即使包含时分秒或小数秒也只保存付款日期；不得用记账日期、上传日期、当前日期或文件名补值。电子回单号码严格必填，交易流水号不能替代；
- 文件格式按真实文件头判断，文件名只用于读取文件，不能作为日期、金额、号码、状态或方向真值；普通日志不输出完整识别正文，仅保留 SHA-256（安全散列算法）摘要、行数和平均可信度用于追踪；
- 单页电子 PDF（便携式文档格式）发票先并行校验页数并调用 [server/services/localOcr.ts](../server/services/localOcr.ts) 的 `pdftohtml -xml`（PDF 坐标文字提取）。价税合计、税额、开票日期、发票号码、开票名称、购销双方名称与税号、原始坐标节点全部完整时，使用 `pdf_structured_fast`（PDF 结构化快速识别）作为业务证据，跳过整页渲染、PaddleOCR（飞桨文字识别）和 Tesseract（开源文字识别），再执行发票结构、正金额、红字／作废、字段完整、主体和业务方向门禁。扫描件、多页文件或任一核心字段不全时不进入快速路径，继续按安全渲染后的 PaddleOCR（飞桨文字识别）与电子文字层交叉校验；
- 快速路径的每个坐标字段还必须能在同一份电子文字层原文中逐项复核，金额与税额按分精确对照；坐标切列、节点顺序或原文不一致时不得进入快速路径。该窄范围优化不删除其他 PDF（便携式文档格式）及图片发票的可见页面和独立证据双路安全门禁；
- 图片发票仍按既有独立复核规则处理；银行回单不再调用 Tesseract（开源文字识别），而是固定由 `PP-OCRv6_medium`（第六版中型模型）识别。PDF（便携式文档格式）银行回单先校验容器、页数和页面尺寸，再把第一页按最长边 4000 像素、总计 900 万像素上限动态降档渲染，并只把该受控临时图片交给第六版中型模型；多页回单仍不自动入账；
- 银行回单切换为单一模型后，`INDEPENDENT_EVIDENCE_MISSING`（独立证据缺失）和 `INDEPENDENT_EVIDENCE_CONFLICT`（独立证据冲突）不再作为新银行回单的阻断原因，也不得因为 Tesseract（开源文字识别）漏字、表格列错序或中文名称误读而覆盖第六版中型模型的字段。该调整只移除第二引擎比较，不放宽真实性及业务门禁；
- 银行回单的左右并列表格优先按第六版中型模型返回的坐标恢复付款／收款单元格；坐标结果完整时直接作为该模型的业务字段，全文顺序解析只补齐坐标缺失项。同一模型的坐标解析与顺序解析不是两条独立证据，二者因表格串列产生差异时不得生成字段冲突阻断；解析策略第八版兼容工行短横线和点号时间戳并统一提取付款日期，未消费的旧任务可由用户重新选择同一原件后重算；
- 银行回单整图遗漏付款人或收款人主体时，只对已定位的户名、付款／收款角色和账号区域使用同一 `PP-OCRv6_medium`（第六版中型模型）执行一次受限增强复扫；增强裁片只补目标主体，不构成独立通道，也不覆盖整图金额、日期、电子回单号码、状态或方向。双列表格按坐标隔离两方，角色版式按标签与同一单元格账号绑定，长主体仅在本单元格内跨行并在账号、开户行、金额、摘要或另一角色处停止；唯一付款账号不得复制、回退或猜测为收款账号。主体／账号缺失、相同、跨列、多值、归属冲突或低置信均失败关闭。合同银行回单解析版本升级为 `contract-bank-receipt-parser-v11`（合同银行回单解析第十一版）；旧解析版本且尚未消费的任务自动升级重跑，不沿用旧主体与账号结果；
- 新银行回单必须同时通过：显式请求及任务级返回模型为 `v6_medium`（第六版中型模型），逐行结果只要携带模型版本就不得与之冲突；同时继续校验真实文件格式与单页限制、正文“银行＋回单”真实性特征、行级平均置信门槛、付款时间、正金额、电子回单号码、付款／收款双方户名及账号完整、双方账号不同、票据未作废、字段内部无冲突。收付方向只按已配置结构化主体的法定全称精确判断：单一内部主体与外部对方之间继续判定回款／付款；仅当资产合同已明确设置“工程咨询划拨科技支付”时，付款人为工程咨询、收款人为科技公司的内部回单才判为有效支出。未配置该资金方式、反向划拨或两方均为外部主体时仍保持方向未知并隔离；
- 结构化快速路径以完整坐标字段和原始文字节点作为单一结构化证据，不再生成“购销双方两路结果不一致”的线性排版伪冲突；未进入快速路径的 PDF（便携式文档格式）和图片发票仍保留既有独立证据缺失／冲突门禁。发票或回单出现正文缺字段、内部冲突、低可信、红字／作废、状态未知、第三方或方向错误时均阻止自动入账；批量识别中单份文件失败只返回该文件的失败结果，不中断后续文件。
- 路由只把真实格式和结构化字段写入 `snapshot_json`（结构化快照），把完整正文转换为 `evidence_text_hash`（证据摘要）；识别方法、运行版本、方向、票据状态、阻断原因和警告独立留痕，普通日志和数据库均不保存完整 OCR 原文；
- 两阶段流程允许发票识别完成后立即由 `POST /financial-registrations`（财务登记接口）保存待回款草稿，也允许同时保存金额尚未补齐的银行凭证；登记补充接口可反复追加发票和银行凭证，并与已有明细及对应关系一起锁定，按剩余发票额度创建本批银行事实和部分对应关系。合同方向已在合同创建时由分类确定；新增发票、银行凭证、对应关系、任务消费、银行凭证确认、方向一致性复核、回款费率快照及合同状态重算在同一事务内完成；任一任务缺失、已消费、来自其他合同、类型／方向错误、主体不配对、累计结算超额或写入失败都整组回滚；旧单条新增入口继续拒绝新建。
- 工程咨询划拨科技模式把科技对外付款登记分为创建和追加两条明确路径：没有开放登记且仅有科技对外付款时使用无登记编号的 `external-payments`（科技对外付款创建接口）；已有开放登记时使用带登记编号的 `external-payments`（科技对外付款追加接口）。已有科技对外付款后只补发票时，不调用任何科技对外付款接口，而是使用 `settlements`（登记补充接口）并提交空 `bankOcrJobIds`（银行回单识别任务编号数组），将发票挂入原登记后重建对应关系。开放登记无发票时仍可继续追加科技对外付款，单独补发票也不得被“本次必须同时新增银行凭证”门禁阻断；
- 旧未消费任务自动升级识别后，以新结果最终确定的付款角色作为唯一分流事实：工程咨询付款、科技收款进入工程划拨；科技付款、合同对方收款进入科技对外付款。页面和服务端都不得复用刷新前分类。科技对外付款任务提交到普通 `settlements`（登记补充接口），或工程划拨任务提交到科技对外付款接口时，服务端必须在消费任务和写入财务事实前拒绝；刷新失败、角色冲突或目标开放登记不唯一同样失败关闭；
- 财务任务保存失败类型、重试次数、工作令牌和 15 分钟租约。相同摘要处于基础设施失败或租约已过期时，再次上传会复用已存原件并接管原任务；有效租约内返回处理中错误，业务阻断、文件错误和普通识别失败保持原结果。完成或失败更新必须匹配当前工作令牌，旧实例晚到结果不能覆盖接管后的新结果；
- 识别策略升级不能由只读查询直接改写历史任务。已消费任务及其正式回款／付款记录继续使用当时保存的识别方法、引擎版本、结构化快照、证据摘要和阻断结论，不因停用 Tesseract（开源文字识别）自动重算；尚未生成正式记录且仍使用旧方法／引擎／解析策略的银行回单，由待登记查询返回需要更新标记，页面随后按顺序自动调用独立重试接口，以第六版中型模型和当前解析版本升级重跑，旧状态可以是 `blocked`（已阻断）或 `verified`（已验证）。重跑必须在摘要锁和工作令牌保护下递增重试次数，清空本轮临时结果，并在覆盖前把旧状态、方法、引擎／解析策略版本、证据摘要及阻断码写入不可变审计；有效租约、已消费任务、已有正式记录任务和不匹配的旧工作令牌仍拒绝接管；
- 新回款和付款记录保存电子回单号码、付款时间、付款／收款双方户名及账号和金额；交易流水号、银行、币种、记账日期及旧 `proof_no`（旧版混合号码）仅保留历史兼容，不进入新登记快照、页面字段或必填门禁，也不自动猜测回填；

#### 四区全量核对与检查点

- [server/scripts/audit-four-area-documents.ts](../server/scripts/audit-four-area-documents.ts) 按盘点清单核对丰台、海淀、朝阳、门头沟四区合同、发票和银行回单；启动时复核四区集合，执行前逐文件重新计算大小及 SHA-256（安全散列算法）摘要，源文件变化时停止采用该条结果；
- 审计结构版本为 4，合同第六阶段审计策略固定为 `automatic-risk-review-2026-08-07-v12`（自动风险复核第十二版）。检查点只有在结构版本、审计策略版本、生产自动采用策略版本、`OCR_MODEL`（识别模型配置）、上传声明分类、识别类型、公司身份配置摘要、文件相对路径、文件摘要和识别上下文全部一致时才可复用。`--ocr-model`（审计模型参数）允许 `v4_mobile`（第四版移动模型）、`v5_server`（第五版服务器模型）或 `v6_medium`（第六版中型候选模型），合同回归可通过 `--declared-category main_business` 传入上传时锁定的声明分类；模型、声明分类和自动采用策略版本同时写入配置摘要及每条结果／重复引用记录。合同审计直接调用生产 `decideContractAutomaticOcrAdoption`（合同自动采用决策）计算 `automaticReady`，不再以 `fieldScore=100` 判断；压缩结果继续保存字段和候选的 `ocrConfidence`（识别原始置信度）、`fieldScore`（字段规则评分）以及任务／字段／候选的模型版本。切换模型、声明分类或自动采用策略后旧检查点必须失效，并应使用新的输出文件；合同上下文至少包含主合同／补充协议／终止协议金额语义及源文件格式，财务上下文包含凭证类型、源文件格式和本轮公司身份配置。相同字节但扩展名不同的文件不得跨解析通道复用；旧结构、旧策略、旧模型、旧声明分类、旧身份配置和旧文件内容均不得混入新一轮结果；
- `--concurrency`（审计并发参数）只允许 1 或 2，默认 1；`--limit`（数量限制参数）先按待处理物理路径裁切，不能按摘要组计数。裁切后的每个物理路径必须先独立执行文件状态、大小和 SHA-256（安全散列算法）核验，再按“摘要＋识别上下文”分组，由组代表执行一次识别；
- 恢复运行不能直接跳过已完成路径：每个检查点对应的源文件仍须重新核对状态、大小和摘要，发生变化时撤销旧完成状态。组代表识别前制作同扩展名不可变临时副本并再次核对副本大小和摘要，识别完成后再复核原路径；任一阶段变化都作废本次结果，防止 `TOCTOU`（检查与使用时序竞争）把新内容记在旧摘要下；
- 只有组代表返回与本轮合同／发票／回单类型匹配、状态枚举合法、字段及警告等必需结构完整且非基础设施失败的结果，其他物理副本才形成带源路径的 `duplicate_reference`（重复原件引用）记录；基础设施失败、外层异常和损坏输出行不计为完成，也不能向同组其他路径扇出完成记录，续跑时必须重新核验并重试。V11（第十一版）策略输出由单个 Node（节点运行时）进程集中逐行追加，两个工作器不会交错破坏 JSONL（逐行 JSON）记录；
- 第七阶段留出集原始 `JSONL（逐行 JSON）` 分片包含路径和业务字段原值，必须保持 `0600` 权限并匹配 `.gitignore（版本控制忽略清单）` 的私有分片规则。`npm run contract:ocr:summarize-holdout` 只读校验 50 个唯一 `SHA-256（安全散列算法）`、固定结构／策略／模型版本和统一配置摘要，输出不含逐文件摘要、路径、字段原值或原始原因的聚合计数。模型统计以顶层 `ocrModel（识别模型）` 为准，兼容旧进程压缩结果未重复序列化字段级模型版本；压缩产物不是生产完整 OCR（光学字符识别）逐行结构，不能替代 HTTP（超文本传输协议）上传与回读验证。该留出集只完成字节级精确摘要隔离，不代表合同族或近重复严格隔离；冻结识别结果写入隔离数据库的验证只能称为“冻结识别结果数据库持久化回放”，不能称为真实 OCR（光学字符识别）或 HTTP（超文本传输协议）端到端测试；
- 发票公司方向必须由同一结构化主体的法定名称与纳税人识别号成对命中，不允许名称与其他主体税号交叉匹配。默认管理主体为“北京羽隶工程咨询有限公司＋91110116MA01G3U20C”和“北京羽隶科技有限公司＋91110116MA01BN342Y”。发票购销一方精确命中任一已配置主体、另一方为外部主体时才确定进项或销项；两方都是内部主体时视为内部业务，两方都不是已配置主体时视为第三方凭证，两种情况均禁止自动入账；
- 合同领域服务先从根合同甲乙双方中解析唯一 `contractCompanySubject`（合同公司主体）：必须恰好一方命中已配置结构化主体，双方均命中或均未命中都拒绝财务登记。识别器随后将发票或回单命中的内部主体与该合同主体严格比较；科技公司凭证误挂工程咨询公司合同，或工程咨询公司凭证误挂科技公司合同时，方向保持未知并阻断，不得因两家公司同属管理范围就跨主体自动挂账；
- 银行回单方向不依赖预配置银行账号，只按付款人／收款人户名与上述两个管理主体的规范化精确匹配判断；银行账号继作为必识别字段、主体配对和防重证据保存。明确为内部划拨模式的资产合同，工程咨询向科技的已确认未冲正回单按真实付款日期计入工程咨询经营支出；科技向外部合同对方的付款另存为履约核销记录，不再重复计入支出。其他未明确配置的内部转账仍保持方向未知，页面显示“识别完成 · 待核对收付方”。

#### 盖章版核验与差异复审

- [server/services/contractSealWorkflow.ts](../server/services/contractSealWorkflow.ts) 以用印审批通过时的甲方、乙方和金额快照作为差异比较基准；盖章版合同日期独立作为归档同步日期。上传盖章版只创建核验批次、不直接把合同改为生效，但当前盖章文件写入成功后会立即触发子协议从台账切换到主合同附件；最终生效和解除目标终止仍只能由核验归档事务完成；
- 租赁续签盖章归档同时锁定新主合同和续签来源：先核对来源仍是当前谱系叶子、来源到期日未变化，再核对盖章版新合同租期和金额与审批版一致；通过后只把新合同推进为生效并在新旧合同写入谱系审计，不推进来源合同金额、租期或财务。新旧合同后续发票、付款、科技最终对外付款、完成率和冲正均按各自根合同独立计算；退租／还车继续按当前叶子自身金额和付款精确分流；
- 甲方和乙方分别与草拟审批快照执行名称规范化后的严格比较。可靠识别后任一方不同都会形成独立差异并要求复审；字段缺失或证据不足则进入重试状态，不得冒充为名称不一致。某一方需要重试时，另一方已经由可靠证据确认的不一致仍会单独保存和展示，不得被整单重试状态清空或误报为一致。前端在详情页内嵌页签中展示逐方三态对照，不再使用盖章核验弹窗；
- 盖章核验按识别服务输出的甲方、乙方和金额最终规范值判断是否可比较，不再把兼容 `confidence`（评分字段）或 `fieldScore`（字段规则评分）精确等于 100 作为内容一致的必要条件。文档来源的三项核心值完整且合法时，主体按 NFKC（兼容等价规范化）、大小写、空白及标点清理后的文本比较，金额按整数分比较；全部相等进入待归档，非满分分数不能单独把正确核心值改成“无法核验”。仅由 `rule`（规则推导）或人工来源产生的相同值不能替代文件识别证据；`ocrConfidence`（识别原始置信度）、`fieldScore` 以及项目名称、分类、日期的候选警告继续完整保存用于诊断；
- 核心值与快照不一致时采用更严格的差异证据门禁：精确验证结果可以形成差异；非满分结果只有来源为 `mixed`（多来源）、字段规则分不低于 90，且该字段没有候选冲突、低置信、不完整、截断、损坏、未识别到或识别风险警告时，才形成结构化差异。单一文字层／单一识别通道的非满分不一致以及带风险警告的不一致进入重新识别，避免把转写错误误报为合同内容变化；
- 甲方、乙方或金额缺失，金额不能转换为合法整数分，或者非基础设施识别失败没有形成可比较核心值时进入 `review_required`（需要重新识别），不得生成空值差异或放行归档。盖章版识别出真实有效日期时保存该日期及 OCR（光学字符识别）来源；签章页标签与手写日期被印章噪声打散时，可使用同页原文中与审批日期精确相等且不晚于上传日的日期证据，非签章页日期不得借用。日期仍缺失或非法时自动采用盖章文件上传日并保存 `upload_date`（上传日期）来源，不触发逐字段人工确认。上传日兜底不是 OCR（光学字符识别）自动结果，不得冒充识别值，且只适用于盖章归档，不回填草拟阶段；
- 本地识别进程、渲染器或文件读取异常统一标记为基础设施失败，只能重试识别或重传文件，不能以人工填写绕过；
- 高可信关键字段与审批快照不一致时形成结构化差异，财务必须填写说明并发起复审；合同进入审批中，目标审批人通过后核验转为差异已批准，驳回后核验转为差异已拒绝且合同进入已拒绝终态，不再返回差异说明阶段；
- 只有自动核验通过且差异不存在，或差异已经总经理复审通过，才能最终归档；归档事务把盖章版有效识别日期或上传日同步写入合同签订日期及来源，并同时写入当前盖章文件版本、合同状态和完整审计；
- 新盖章文件会替代旧的未完成核验。上传、重试、差异提交和归档均校验合同版本号，阻止两个操作窗口互相覆盖。重试必须在同一事务内按新识别结果重新计算字段可用性、差异和状态；旧工作实例、非当前文件或版本冲突不能覆盖当前核验；
- 历史盖章核验记录兼容只含 `confidence`（兼容评分字段）而没有独立 `ocrConfidence`（识别原始置信度）的旧结构，读取时继续把 `confidence` 解释为 `fieldScore`（字段规则评分）并保留原状态。只读查询不得把旧 `review_required`（需要重新识别）记录静默改成可归档；未完成旧记录需要按新语义前进时必须由用户显式重新识别。已归档、差异已批准、差异已拒绝和已替代记录不得因规则升级被重新分类。

- 总经理审批目标在提交时按唯一活动总经理账号解析，管理员执行目标按唯一活动管理员账号解析；管理员不参与审批，其他管理员组账号也不能抢占已指定任务。批准后下载接口只接受申请文件快照编号，响应成功传输后才记录下载事实；所有指定文件均已下载才允许填写可选处理说明并办结；
- 响应状态与下一步固定对应：`pending_approval`（总经理审批）、`approved`（管理员待办）、`processing`（管理员执行中）、`completed`（流程完成）、`rejected`（已驳回）或 `withdrawn`（员工已撤回），每个节点以业务职位和真实姓名组合展示。
- 总经理批准或驳回时只推进申请的 `updated_at`（更新时间），保留原 `applicant_seen_at`（申请人查看时间），使驳回稳定进入员工未读计数。确认已读服务必须接收 1 至 100 个 `requestIds`（申请编号），去重后仅更新当前员工实际指定且已产生结果的记录；未传编号、待审批记录、其他员工记录和当前页之外记录均不会被清除；响应返回本次确认数量及剩余未读数量。
- 撤回与审批事务对同一申请执行行锁和期望版本校验，员工只能撤回自己的待审批申请；撤回将本人已读时点同步推进，避免自己的操作形成未读提醒。重提只接受同员工、同合同最新叶子的驳回／撤回记录，重新读取合同、当前附件、唯一审批／执行账号及员工锁定签名并生成下一次申请，旧行和旧物理申请单不修改；
- 普通创建发现该合同最新叶子仍可重提时返回 `CONTRACT_DOWNLOAD_USE_RESUBMIT`。重提事务同时依赖上次申请唯一后继、申请链次数唯一和活动申请唯一索引；数据库唯一冲突转换为明确的 409 业务错误。响应提供跨尝试申请链历史；员工“当前申请”只返回每条链最新且尚未完成的尝试，“历史申请”只返回最终已完成记录并由服务端分页。旧驳回／撤回尝试不单列，继续作为完成申请的链内事件展示。签名申请单从第二次起注明提交次数及原申请编号。
- 总经理待审批列表继续按本人 `target_approver_id`（目标审批人编号）和待审批状态过滤；审批记录按本人 `approver_id`（实际审批人编号）过滤，只包含已批准、执行中和已完成记录，并按决定时间、更新时间倒序分页，显式筛选已驳回固定拒绝。旧驳回详情的直接读取权限保持原边界，但不进入列表；详情及申请链历史不能从本人旧驳回尝试读取后来分配给其他总经理的新尝试。
- 管理员待办继续按本人 `target_executor_id`（目标执行人编号）返回已批准和执行中任务；办结历史仅允许 `admin`（管理员）角色按本人 `executor_id`（实际执行人编号）读取已完成记录，并按完成时间、更新时间倒序分页。详情和申请链使用同一隔离条件，其他管理员及非管理员角色不能读取本人以外的办结记录。

```typescript
export const getTenantAccessToken = async () => {
  // 检查缓存
  if (cachedTenantToken && cachedTenantToken.expires_at > Date.now()) {
    return cachedTenantToken.token;
  }

  // 获取新 token
  const response = await fetch(
    "https://open.feishu.cn/open-apis/auth/v3/tenant_access_token/internal",
    {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        app_id: process.env.FEISHU_APP_ID,
        app_secret: process.env.FEISHU_APP_SECRET,
      }),
    },
  );

  const data = await response.json();

  // 缓存 token（提前 5 分钟过期）
  cachedTenantToken = {
    token: data.tenant_access_token,
    expires_at: Date.now() + (data.expire - 300) * 1000,
  };

  return cachedTenantToken.token;
};
```

```typescript
export const handleFeishuError = (error: any) => {
  if (error.code === 99991663) {
    throw new FeishuAPIError("Token 已过期", error.code);
  }

  if (error.code === 99991668) {
    throw new FeishuAPIError("应用权限不足", error.code);
```

### 重试机制

```typescript
export const retryFeishuAPI = async <T>(
  fn: () => Promise<T>,
  maxRetries = 3,
): Promise<T> => {
  let lastError: Error;

  for (let i = 0; i < maxRetries; i++) {
    try {
      return await fn();
    } catch (error) {
      lastError = error as Error;

      // 如果是 token 过期，清除缓存重试
      if (error instanceof FeishuAPIError && error.code === 99991663) {
        cachedTenantToken = null;
      }

      // 等待后重试
      await new Promise((resolve) => setTimeout(resolve, 1000 * (i + 1)));
    }
  }

  throw lastError!;
};
```

```typescript
import crypto from "crypto";

// 验证飞书事件签名
export const verifyFeishuSignature = (
  timestamp: string,
  nonce: string,
  encryptKey: string,
  body: string,
  signature: string,
): boolean => {
  const data = `${timestamp}${nonce}${encryptKey}${body}`;
  const hash = crypto.createHash("sha256").update(data).digest("hex");

  return hash === signature;
};

// 处理飞书事件
export const handleFeishuEvent = async (event: any) => {
  switch (event.type) {
    case "url_verification":
      // 首次验证
      return { challenge: event.challenge };

    case "event_callback":
      // 处理具体事件
      await processFeishuCallback(event.event);
      return { success: true };

    default:
      console.warn("未知的飞书事件类型:", event.type);
      return { success: false };
  }
};
```

## 第十二阶段合同候选生成扩展

- 本阶段只扩展项目名称、金额和签署日期的候选生成，不修改候选排序、`highest-qualified-candidate-v3`（最高合格候选第三版）安全门禁或自动采用标准；新增候选仍必须通过第十一阶段B的来源、语义、冲突、作用域和可见页面证据校验。
- 项目名称新增首页普通合同／协议／合同书标题、书名号内单行或跨行标题、合同名称字段的文档类型剥离候选，以及具有明确前后边界的服务对象描述。普通正文对象候选标记为 `body_description`（正文描述来源），不能单独满足自动采用条件；非主营合同中，“委托／聘请……就／针对／围绕具体项目服务对象……提供／开展／承担／完成服务”的闭合句式可作为强语义证据，但仍必须由同页 PDF（便携式文档格式）文字层和可见 OCR（光学字符识别）精确同值复核。纯合同类型、单位名称、付款条款、背景项目和代词项目继续拒绝。
- 金额生成器按同一条款中的每个金额锚点分别绑定最近角色，支持合同价款、服务费用总额、协议金额、含税合同金额、费用共计、收费金额以及“咨询费／顾问费／服务费总价款”等结构；明确合同金额标签后的紧邻纯数字可形成候选。付款金额、税额、普通分项服务费、周期单价继续保留各自角色，不能升级为合同金额；百分比、千分比、未税金额和增值税额不会继承前一个合同总额角色。
- 日期新增正式订立序言和强签章页落款候选。签章区只在局部存在唯一合法日期，或双方栏位出现同一日期时生成；两个不同合法日期、履约／付款／验收／生效日期及首页无角色裸日期均不猜测。
- 冻结12份诊断集在完全复用原 OCR（光学字符识别）文字的条件下，项目名称正确候选覆盖由1/12提升至11/12，主合同明确金额由5/10提升至10/10，签署日期由1/8提升至6/8；剩余1个项目和2个日期均属于原文未包含正确值。日期空值污染和错误自动采用均为0；付款、税额、服务费、单价等低风险角色可进入诊断候选，但仍被既有金额过滤与安全门禁阻断。
- `PP-OCRv6_medium`（第六版中型模型）、数据库结构、API（应用程序接口）和原始 OCR（光学字符识别）输出结构保持不变。

## 第十三阶段非主营多样式合同识别

- 非主营识别继续使用统一候选漏斗，不按客户、文件名、目录名或固定页码编写模板。首页独占一行的 8 至 32 位纯数字条形码流水号从跨行标题窗口中排除；数字与业务标题位于同一行时不删除，避免误伤“2026 年度审计”等合法名称。
- 通用“技术咨询服务合同”首页没有项目名称时，服务可识别“甲方已与第三方签署《具体项目服务合同》”并在后文再次明确委托乙方提供同一项目服务的闭合结构。引用标题与本次委托缺一不可；多个不同引用标题、一般法律引用、元数据标题和单一正文来源继续失败关闭。
- “咨询服务费总价款／技术咨询服务费总额”先按整份合同总额分类，再处理普通服务费；“合同金额的 50%／百分之五十”及其后人民币金额固定归为付款节点。分期比例、首期款、税前价和税额不会再因包含“合同金额”字样取得总额角色。
- `PDF（便携式文档格式）`文字层项目与金额仍须同页可见 OCR（光学字符识别）同值同角色复核；纯扫描非主营闭合服务对象至少需要 300 DPI（每英寸点数）与 480 DPI（每英寸点数）两档可见结果同值。解析版本升级为 `contract-structure-v13`（合同结构第十三版），使旧任务明确进入重新识别。

## 第十四阶段资产车辆租赁识别

- 固定月租资产租赁事实从房屋、场地扩展至小客车、车辆和汽车租赁，仍只读取正文租赁期限、月租和明确总额，不建立车辆档案或新的费用模型。首页“公司租个人小客车协议”等标题只剥离文档类型，规范为资产合同名称。
- 资产租赁可接受明确“甲方／乙方＋出租方／承租方”标签后的自然人姓名，但必须同时具备 2 至 6 个中文姓名字符及相邻完整 18 位身份证号；非租赁合同、无身份证号或普通短残片继续按机构主体门禁拒绝。
- 租赁月数按日期周年计算：结束日与起始日同日时不重复计算首尾月份；`2025-10-31` 至 `2026-10-31` 为 12 个月，月租 780 元对应合同租金总额 9,360 元。正文明确月数或总额仍优先；押金、保险保额、首月租金比例违约金、燃油／路桥／停车／洗车／维修／保险等另行费用不得进入合同总额。
- 解析版本升级为 `contract-structure-v14`（合同结构第十四版），旧车辆租赁部分结果重新识别后使用新主体、名称及周年月数规则。

## 外部盲测数据源离线导入

- [server/scripts/lib/contractOcrExternalIntake.ts](../server/scripts/lib/contractOcrExternalIntake.ts) 提供独立只读准入层，只扫描外部目录，校验文件结构，计算 `SHA-256（安全散列算法）`，合并精确重复，加载显式历史曝光来源并按合同族传播排除；该模块不导入识别服务、数据库或业务路由，也不启动子进程。

## 开票申请材料服务

`server/services/invoiceApplicationMaterial.ts` 负责三联单和非主营甲方材料的最小安全处理。它只为主营固定三联单读取“其他费用－本次付款”金额，不识别开票内容、财务方向或非主营材料金额。

### 材料决策

- 主营项目合同固定使用 `material_need_seal`（有材料需盖章）：新申请由服务端根据在线填写的工程项目名称和本次付款金额生成三页 PDF；合同金额取主合同当前有效金额，以前累计只汇总非草稿、非驳回的有效申请，本次累计按“以前＋本次”计算。在线三联单采用参考原表的紧凑居中比例：增加标题上方留白，标题与主表整体下移，主表收窄并压缩行高，右侧联次文字同步缩小并靠近表格；工程项目名称行不绘制外围方框，加粗项目内容按标签实际文字宽度紧跟冒号，并继续为右侧“单位：元”预留固定安全空间。PDF 摘要、金额快照和合同当前金额在提交时再次校验，任一变化均要求重新生成。历史 XLS／XLSX 三联单继续使用原有结构检查路径。
- 非主营项目合同支持 `material_need_seal`（有材料需盖章）、`material_no_seal`（有材料不需盖章）和 `no_material`（无材料）。前两种必须上传文件，第三种不得混入文件；只有第一种生成管理员盖章待办。
- 资产类合同在材料服务层同样直接拒绝，防止绕过前端入口。

### 真实文件与容器门禁

- 服务不信任浏览器上报的媒体类型，必须同时校验扩展名、真实文件头和可完整解析性。
- XLSX（电子表格）必须是完整 ZIP（压缩包）容器，存在内容类型和工作簿定义，并限制容器条目数、解压总量、工作表数量和单元格范围，阻止压缩炸弹和资源耗尽。
- XLSX（电子表格）不得含宏、外部链接或 ActiveX（主动式组件）。历史固定模板中的内嵌对象只保留在不可变原件，不进入自动打印派生文件，避免无人值守转换执行内嵌内容。
- PDF（便携式文档格式）必须可解析、未加密且页数合法；JPG（联合图像专家组格式）和 PNG（便携式网络图形）必须能完整解码并符合像素限制。

### 预览和打印派生

- 原始 Excel（电子表格）作为不可变事实保存；服务返回 SHA-256（安全散列算法）摘要，路由必须与实际入库文件摘要一致。
- 主营预览只将“其他费用”工作表转为最多 200 行、50 列的文本矩阵，其他工作表的文本不出现在业务响应。
- XLSX（电子表格）和 XLS（旧版电子表格）均先重建为只含“其他费用”的安全派生工作簿，再使用独立临时 LibreOffice（文档转换工具）配置导出 PDF（便携式文档格式）；其他工作表和内嵌对象不进入自动转换。
- 转换不可用时才回退为只含“其他费用”的单工作表 XLSX（电子表格）；不得回退为包含其他工作表的完整原件。
- 旧版 XLS（电子表格）无法原样修改工作簿定义时，使用只包含目标表值与公式的派生 XLSX（电子表格）兼容输出，原 XLS（电子表格）仍完整保存。

### 主营本次付款金额

- 仅扫描原始“其他费用”工作表完整单元格，不使用 200×50 的预览矩阵。
- 以 NFKC（兼容性规范化）处理文本，只接受固定“本次付款／本次付款金额”列头、明确“元”单位及“合计／总计”行。
- 读取该列从表头下一行至合计上一行的明细，全部按分求和。明细格禁止公式；合计格只允许精确的 `SUM(明细范围)`（求和公式），且必须带有可核对缓存值并与明细相等，缺少缓存同样阻断。结构标签和单位不得由普通、数组或共享公式缓存伪造，单位必须唯一且位于付款表头上方；零宽格式字符在比对前统一移除。日期、百分比、科学计数、错误格、负数、三位以上小数、空值、结构缺失和多值冲突均阻断。
- 付款列、付款表头、合计行和金额单位必须可见，付款列明细及合计不得位于多单元格合并范围；正数格的打印显示值必须与底层数值按分一致，空白显示、自定义字面量或缩放格式不能冒充另一金额。
- 上传前检查只返回金额分值和来源单元格，不保存临时文件。正式材料上传及提交审批会从已保存原件再次提取并核对摘要和申请金额，避免客户端篡改。

### 申请单单签、双签和版本

- 员工提交时，服务在事务内读取本人当前锁定签名，同时固化员工档案中的部门、职位和姓名，规范化为 PNG（便携式网络图形）快照，再与合同、额度、本次开票、对方开票信息和材料列表生成一页 A4（国际标准纸张）单签申请单；签字栏显示“部门 职位 姓名 时间”。
- 总经理通过时不接收客户端上传的签名图片，服务端重新读取本人锁定签名，并从已固化的申请人签名路径重算摘要后，生成同页双签申请单。驳回不伪造总经理签名。
- 两类生成文件分别版本化，新版只将旧版标记为非当前，不覆盖或删除旧 PDF（便携式文档格式）。预览必须核对当前文件编号、物理路径和 SHA-256（安全散列算法）摘要。
- 单页申请单对超长字段、材料清单和审批意见使用有界换行；签名区位置固定且渲染前检查剩余高度，无法安全落在单页时明确阻断，不允许静默裁切签名。完整业务内容仍以系统详情和原始材料为准。

### 额度和正式发票覆盖

- 资格及提交都以主合同当前有效金额为基础，正式发票金额与尚未被发票覆盖的活动申请余额分别扣减，不重复扣减已分配部分。提交、后续状态动作以及既有正式发票的单笔／整组确认、删除、冲正均先取得根合同事务锁，再锁申请行或发票行并重算，防止并发超额和交叉死锁。
- 正式发票仍由现有合同财务登记创建；开票申请服务只读取已建档且未冲正的发票事实，按分执行 FIFO（先进先出）分配。发票只能覆盖在其建档之前已提交的申请，避免历史发票错误覆盖新申请。
- 分配变化会写入审计。管理员已登记开具且申请获得正式发票全额覆盖后才自动完成；只有全额覆盖但尚未登记开具时继续停留在待开具环节。正式发票冲正、删除或金额变化后失去全额覆盖时自动回开为待财务登记，原签名、审批、盖章交付和历史分配审计继续保留。
