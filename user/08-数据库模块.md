## 表结构

> 说明：当前生产环境以 `server/db/index.ts` 中的 PostgreSQL 建表语句为准。  
> 本节部分历史示例保留了旧字段命名，仅用于理解业务关系，不作为迁移执行脚本。

### 1. Users（用户表）

```sql
CREATE TABLE IF NOT EXISTS users (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  email TEXT,
  feishu_user_id TEXT UNIQUE,
  feishu_username TEXT,
  avatar_url TEXT,
  role TEXT DEFAULT 'user',
  is_active BOOLEAN DEFAULT 1,
  last_login_at DATETIME,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_users_feishu_user_id ON users(feishu_user_id);
CREATE INDEX idx_users_role ON users(role);
```

#### 员工编号一致性

- `users.email`、`users.mobile`、`users.department`、`users.position` 和 `users.employee_no` 均允许为空，以支持不属于员工体系的BOSS和董事长轻量账号
- `users.employee_no` 是员工账号编号的唯一数据来源，创建员工账号时由后端自动生成，编辑时可由管理员修改
- 数据库通过条件唯一索引 `uq_users_employee_no` 阻止非空员工编号重复
- 创建员工账号时后端在同一事务锁内扫描已有有效编号并写入账号与员工档案；创建BOSS或董事长账号时保持为空且不创建 `employee_profiles`
- 用户接口修改编号时，在同一事务内同步 `employee_profiles.employee_no`
- 用户接口修改编号时不更新 `employee_documents.file_name`，已归档资料的文件名和文件内容保持管理员上传时的状态
- 数据库启动时不再为空编号账号自动补号；新账号编号只在用户创建事务中生成
- 数据库启动迁移只用账号中的非空编号修复 `employee_profiles` 基础档案记录，不会改写 `employee_documents` 人事档案文件；入职模板下载优先读取账号中的最新值

```sql
CREATE UNIQUE INDEX IF NOT EXISTS uq_users_employee_no
ON users(employee_no)
WHERE employee_no IS NOT NULL AND BTRIM(employee_no) <> '';
```

#### 个人电子签名表 (`user_signatures`)

```sql
CREATE TABLE IF NOT EXISTS user_signatures (
  user_id TEXT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  signature_path TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

- 每个账号只能首次确认一份个人电子签名；记录存在后上传和删除接口均拒绝修改
- 表内只保存受鉴权保护的图片路径，不保存图片数据或公开地址
- 转正流程签署时会把当前个人签名复制到 `probation_signature_records`，历史签名不依赖本表当前内容

#### 管理员代管签名表 (`user_delegated_signatures`)

```sql
CREATE TABLE IF NOT EXISTS user_delegated_signatures (
  user_id TEXT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  represented_user_id TEXT REFERENCES users(id) ON DELETE SET NULL,
  represented_user_name TEXT NOT NULL,
  signature_path TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

- 该表只为兼容历史代签审计数据保留；当前接口和页面不再新增、读取或维护代管签名
- 新转正流程中的员工、总经理、管理员和董事长均只调用各自 `user_signatures` 记录

### 8. LeaveBalances（假期余额表）

```sql
CREATE TABLE IF NOT EXISTS leave_balances (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id),
  leave_type_code TEXT NOT NULL REFERENCES leave_type_configs(code),
  year INTEGER NOT NULL,
  total_days NUMERIC(5,1) NOT NULL,
  used_days NUMERIC(5,1) NOT NULL DEFAULT 0,
  pending_days NUMERIC(5,1) NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE(user_id, leave_type_code, year)
);
```

**假期余额同步口径：**

- 年假以 `leave_type_configs.default_days` 作为所有活动账号的基础额度；有有效入职日期时再按工龄上调，旧版年假说明在启动时幂等更新
- 假期类型默认天数变更时，仅同步当年 `total_days` 仍等于旧默认天数的余额记录
- 管理员手动调整过的个人余额不会被假期类型默认天数覆盖
- 年假个人总额低于基础额度时会在读取时自动补足；补足只更新 `total_days`，不清零 `used_days` 或 `pending_days`
- 调整个人余额时必须满足 `total_days >= used_days + pending_days`，检查和更新在同一事务内加行锁完成
- 启动迁移会识别“999 天且不校验余额”的旧版事假哨兵配置，改为每年 3 天带薪事假，并同步未发生使用或预占冲突的 999 天历史余额

### 8.1 LeaveRequests（请假申请表）

```sql
CREATE TABLE IF NOT EXISTS leave_requests (
  id TEXT PRIMARY KEY,
  request_no TEXT UNIQUE NOT NULL,
  user_id TEXT NOT NULL REFERENCES users(id),
  leave_type_code TEXT NOT NULL REFERENCES leave_type_configs(code),
  start_date TEXT NOT NULL,
  start_half TEXT NOT NULL,
  end_date TEXT NOT NULL,
  end_half TEXT NOT NULL,
  total_days NUMERIC(5,1) NOT NULL,
  balance_allocations_json TEXT,
  balance_reserved BOOLEAN NOT NULL DEFAULT FALSE,
  approval_notice_unread BOOLEAN NOT NULL DEFAULT FALSE,
  rejection_notice_unread BOOLEAN NOT NULL DEFAULT FALSE,
  application_kind TEXT NOT NULL DEFAULT 'normal'
    CHECK(application_kind IN ('normal', 'combined', 'extension', 'supplement')),
  combination_group_id TEXT,
  parent_request_id TEXT REFERENCES leave_requests(id) ON DELETE SET NULL,
  status TEXT NOT NULL DEFAULT 'pending'
    CHECK(status IN ('draft', 'pending', 'approved', 'rejected', 'cancelled'))
);
```

**余额快照说明：**

- `request_no` 使用 `QJ-YYYY-NNNNN` 格式并保持唯一；启动迁移将历史 `LR` 前缀转换为 `QJ`，遇到目标编号冲突时按对应年度最大序号继续编号
- `balance_allocations_json` 保存申请提交时按自然年拆分的天数，跨年申请审批时分别结算对应年份余额
- `balance_reserved` 保存提交时该假期类型是否需要余额检查，避免管理员后续修改类型配置后造成预占天数无法释放或错误扣减
- `approval_notice_unread` 保存审批通过结果是否仍待员工查看；历史记录迁移时默认已读，新的审批通过记录置为未读，员工确认后恢复为 `FALSE`
- `rejection_notice_unread` 保存审批驳回结果是否仍待员工查看；现有最新驳回记录迁移为未读，员工打开对应申请详情后按条恢复为 `FALSE`
- `application_kind` 区分普通请假、组合分段、续假和补假；驳回重提不会改变该业务类型
- `combination_group_id` 关联一次组合提交拆出的多个独立申请；普通组合分段使用 `combined`，组合续假或组合补假分段继续使用 `extension` 或 `supplement`，各记录仍分别保存申请编号、审批状态和余额快照
- `parent_request_id` 将单一及组合续假、补假统一挂到已批准主申请下，并与仅用于驳回重提版本链的 `original_id` 分离；删除主记录时关联值自动置空
- `idx_leave_requests_approval_notice` 和 `idx_leave_requests_rejection_notice` 分别加速审批通过、驳回的本人未读提醒统计
- `idx_leave_requests_combination_group` 和 `idx_leave_requests_parent_request` 分别加速组合详情和主子申请查询
- 新提交和重新提交通过事务行锁预占 `pending_days`，审批、驳回、撤回再按快照转为已使用或释放
- 婚假一次性资格通过 `employee_profiles.id_number` 关联历史申请；提交事务按规范化身份证号获取事务级锁，并检查同一身份证号是否已有审批中或已批准婚假，不新增年度重复资格字段
- 审批中申请撤回时更新为 `draft`，同时将 `balance_reserved` 设为 `FALSE`；草稿重新提交后重新预占余额并恢复为 `pending`
- `cancelled` 仅保留在检查约束中兼容旧备份；数据库启动时会将现有 `cancelled` 记录迁移为 `draft` 并清除余额占用标记，新撤回不再写入该状态
- 草稿手动删除和跨月自动清理均采用硬删除：先删除整条版本链的 `leave_approval_logs` 与 `leave_attachments`，再按版本倒序删除 `leave_requests`，事务提交后清理磁盘附件

**审批人数据规则：**

- `approver_id` 和 `approver_name` 保存提交时选定的具体审批人；普通员工保存活动总经理，总经理保存活动董事长，申请人本人不会被选为审批人
- 查询请假流程时，总经理和董事长的显示身份直接取账号角色名称，不使用员工档案职位覆盖审批角色
- 对应角色没有可用审批人时不创建请假申请，不回退到管理员或超级管理员
- 启动迁移会逐条重算历史待审批申请：普通员工待办分配给活动总经理，总经理待办分配给活动董事长；暂时没有对应审批人时清空旧的错误分配
- 管理员抄送采用角色范围读取，不重复写入抄送明细；管理员和超级管理员可读取全员申请，但不能更新审批状态

### 8.2 人力成本工资表

`employee_documents` 为劳动合同档案增加以下期限字段：

```sql
contract_start_date TEXT,
contract_end_date TEXT,
contract_recognized_at TEXT,
probation_end_date TEXT
```

`employee_profiles` 另行保存待签劳动合同模板的拟定日期：

```sql
contract_template_start_date TEXT,
contract_template_end_date TEXT,
probation_template_start_date TEXT,
probation_template_end_date TEXT
```

归档后还会保存上一期模板预览快照：

```sql
last_contract_template_start_date TEXT,
last_contract_template_end_date TEXT,
last_probation_template_start_date TEXT,
last_probation_template_end_date TEXT,
last_contract_template_position TEXT
```

- 模板日期允许为空，续签合同可只填写合同期限并将试用期保持为空
- 正式合同归档时清空当前四个模板日期字段以锁定下载；历史上一期日期和 `last_contract_template_position` 字段仅保留兼容，不再用于最新版模板预览，未设置当前期限时模板日期保持空白且岗位实时读取员工当前职位
- 启动迁移会使用最近一份已识别正式合同回填缺失的上一期快照，兼容已经被清空过模板日期的员工
- 模板日期不参与正式入职、合同到期和转正数据计算；正式日期继续取已归档劳动合同的识别结果
- 同一员工可保存多条 `document_type='contract'` 的档案记录，构成续签历史
- `employee_documents.document_type='other'` 保存员工提供但不属于固定十类的其他资料；该类型允许同一员工保存多份文件
- `employee_profiles.hire_date` 是系统维护的入职日期快照，来源为该员工第一份已识别完整起止日期合同的 `contract_start_date`；没有可识别合同时必须为空
- `employee_profiles.contract_end_date` 是当前合同结束日期的查询快照，来源为合同档案中最大的 `contract_end_date`
- `employee_documents.probation_end_date` 保存每份劳动合同 OCR（文字识别）出的试用期截止日期；员工转正使用第一份合同的值，续签合同为空不会覆盖
- 不再根据 `hire_date` 推算合同到期时间；启动迁移会清理没有合同依据且恰好等于“入职日期加一年”的旧推算值
- 启动迁移会回填已有识别合同员工的入职日期、当前合同到期日期，以及待提交或已驳回转正记录的合同日期；没有识别合同的历史员工数据不做推算

- 工资基础金额使用无固定小数位的 `NUMERIC`（精确数值）；公式内部按精确十进制计算，返回表格时统一四舍五入为两位小数
- `housing_fund_base` 保存公积金缴费基数，`contribution_base` 保存社保缴费基数；单位和个人公积金均使用前者，单位和个人社保均使用后者
- 单位与个人承担明细不重复存储，由统一计算服务根据月度基础字段实时推导，避免公式修改后出现字段不一致
- 四个手工标记区分自动值和管理员改单值；普通自动重算不覆盖手工值，新上传正式邀请函时仅重置本月工资手工标记，公积金基数、社保基数和个税手工标记不变
- 历史月份保留金额快照；主动生成月份时同步人员成员关系，入职当月加入、离职当月保留、离职次月移除
- 一键删除人事档案时只删除该员工的 `employee_documents`，同时清空 `employee_profiles.contract_end_date`；`employee_salary_profiles` 与 `payroll_records` 保留，来源文件外键通过 `ON DELETE SET NULL` 自动置空
- 批量档案删除与合同日期清空在同一事务中完成；删除过劳动合同时，当前及未来自动工资按无合同档案状态重新同步，历史月份和管理员手工金额保持不变
- 数据库初始化会清理关联用户角色为 `super_admin` 的工资记录，系统维护账号不纳入人力成本数据
- 工资查询、生成、修改和自动同步均排除 `boss`（BOSS）与 `chairman`（董事长）；不删除既有历史记录，但当前角色为轻量账号时不计入人员和人力成本口径
- `payroll_records.version` 为多人修改提供乐观锁；自动工资变化和管理员修改都会递增版本
- `payroll_change_logs` 保存管理员修改前后金额、操作人和时间，随工资记录删除而级联清理
- 个人个税明细识别复用 `payroll_records.individual_income_tax` 和 `tax_is_manual`，每个成功匹配员工递增记录版本；金额实际变化时写入 `payroll_change_logs`
- `payroll_tax_detail_files` 每个工资月份保存一份最新的个人个税明细原件、识别人数、0 元人数及未识别名单；重新上传同月明细时事务替换记录并清理旧原件，支持页面刷新后继续在线预览
- `human_cost_receipts` 保存公司级社保、公积金、个税和实发工资汇总回单；月份为工资归属月份，不是文件上传日期
- `human_cost_receipt_items` 仅保存通过校验的实发工资单笔结果，按收款账号或收款户名精确关联员工，并保存原 PDF（便携式文档格式）的页码及上下位置；来源回单删除时单笔记录级联删除
- 回单识别金额固定保存两位小数；`recognized_item_count`、`total_item_count` 与 `ignored_item_count` 分别记录成功、校验范围及非工资回单忽略笔数
- `recognition_version` 标识识别规则版本；旧版回单在管理员再次打开对应月份时自动进入后台重识别，无需删除后重新上传
- 文件摘要唯一约束只覆盖同一工资月份和同一费用类别，既防止重复汇总，也允许同一原件在确有需要时归入其他月份或类别
- 回单索引覆盖工资月份与类别、识别状态，支持月份切换查询和处理状态轮询
- 用户角色、账号状态、员工状态、档案类型、转正状态、请假状态、半天时段、余额和工资版本均有数据库检查约束；各类历史数据约束独立迁移，单类旧脏数据不会回滚工资版本字段
- 用户角色检查约束支持 `boss`（BOSS）和 `chairman`（董事长）；启动迁移同步更新既有数据库约束，董事长角色与内部兼容保留的最终审批阶段编码保持独立。

- `probation_confirmations.employee_id` 使用唯一索引，确保每名员工只有一条当前转正记录；新账号不预建记录，劳动合同识别出入职日期和试用期截止后再创建

- `probation_confirmations.probation_end_date` 允许为空；第一份劳动合同未设置试用期时保持空值，不能沿用续签合同或历史推算日期
- `probation_confirmations.form_version` 标识员工每次重新提交的在线申请版本，`review_stage` 标识员工、主管、人事部、董事长终审或已完成阶段；数据库继续使用 `general_manager` 值兼容既有记录
- 申请人、部门和职位使用提交时快照生成待盖章底稿，员工后续调岗不会改写已经签署版本
- `probation_confirmations` 在每次提交时固定保存主管、管理员和董事长的账号及姓名快照；当前人员后续改名、停用或换人不会改写该版流程，重新提交的新版本才重新分配
- `probation_confirmations.supervisor_id` 固定为本次签署主管领导意见的总经理账号，`formal_document_generated_at` 仅在董事长完成最终审批并成功生成待盖章底稿后写入
- 待处理的转正审批实例使用条件唯一索引，确保同一转正记录同时最多存在一个待审批实例
- `probation_documents.employee_id` 标识文件所属员工；现有流程文件会从转正记录自动回填员工编号
- `probation_documents.confirmation_id` 可为空，支持直接在职员工补录转正申请表且不生成虚假审批记录；每份文件必须至少关联转正记录或员工档案
- `probation_documents.source_type=generated` 标识系统终审生成的待盖章底稿；`source_type=official` 标识管理员在人事转正档案上传的正式盖章文件；`uploaded` 仅保留历史上传材料，两者均用 `form_version` 绑定申请版本
- `probation_signature_records` 保存四个阶段的签名图像路径、实际操作人、签名类型、签名人姓名、意见、决定和服务端签署时间；同一申请版本的同一阶段只能有一条记录，驳回重提不会覆盖旧版本
- 历史记录中的 `signature_type=general_manager` 仅用于兼容旧代签数据；当前新记录统一使用签署人锁定后的本人签名，`signer_id`、`signer_name` 和 `signature_owner_name` 均记录实际签署人
- `resignation_requests` 保存管理员创建的离职人员记录；新记录使用 `draft`（档案待完善），五类档案齐全后仍保持 `draft` 供管理员预览核对，管理员确认离职时才转为 `approved`（已完成）。旧流程字段继续兼容历史数据，但新流程不再使用员工申请、交接或终审。
- `resignation_requests.employee_id` 采用唯一约束，确保同一员工档案只存在一条离职记录；返聘通过新的账号和员工档案形成新的生命周期。
- `resignation_documents` 固定支持终止 / 解除劳动关系协议书、员工离职交接单、薪资及各类款项结算确认书、离职经济补偿协议书、离职证明；`is_current` 标识当前版本，替换时保留历史版本。
- `resignation_templates` 的新增记录只保存五类管理员 PDF（便携式文档格式）原模板；历史 DOCX（开放 XML 文字处理文档）记录保留兼容，每次上传新模板后读取同类型最新版本。
- `resignation_template_drafts.overlay_json` 保存具体离职记录、模板类型和模板版本对应的字段覆盖值及自定义文字位置；`template_id` 防止模板更新后沿用旧模板草稿，旧 `content_html` 仅保留兼容。
- 管理员确认五类当前档案无误时，在同一数据库事务中更新 `resignation_requests.status`、`employee_profiles.employment_status`、`users.status` 和审计日志；单纯上传齐全不再修改员工或账号状态。

#### 合同编号、关系和金额

> 当前有效关系规则：`contracts.relation_type` 仅允许主合同、补充协议、终止协议；旧 `independent`（独立合同）值在迁移中统一转换为 `main`（主合同）。本节后续旧版本描述仅作历史背景。

- `contract_no_sequence` 在数据库事务中生成 `HT-YYYYMMDD-######`，日期按上海业务时区计算；该值仅作为系统内部流水号。每一份主营业务文件（含主合同、补充协议和终止协议）均以可空的 `business_contract_no` 保存自身原件／二维码完整编号；草拟件没有可靠编号时保持为空，盖章件识别到后再补写。条件唯一索引只阻止两份未撤销有效合同占用同一已识别文件编号。上级关系继续由 `parent_contract_id` 保存，不以补充协议自身编号替代；
- `parent_contract_id` 和 `root_contract_id` 均引用 `contracts`。主合同属于一级，`parent_contract_id` 必须为空且 `root_contract_id` 等于自身编号；补充协议、终止协议属于二级，必须关联一个主合同，且上级编号与根合同编号都等于该主合同编号。领域服务在创建和更新时强制整理上述形状，不允许二级协议继续挂接二级协议；主合同金额为正，金额变更补充协议保存有符号调整额，仅变更付款方式的补充协议固定保存 0，终止协议为负数；
- `relation_type`（合同关系）没有数据库默认值，新增记录必须显式写入上传前选择的关系；枚举检查限制主合同、补充协议、终止协议三类合法值，跨记录的一级上级资格、同项目和同分类关系继续在数据库事务内锁定并复验；历史独立合同在迁移时统一转换为主合同；
- `termination_target_contract_id`（解除目标合同编号）是自引用外键，解除协议仍通过 `parent_contract_id` 和 `root_contract_id` 挂在主合同第二级，但可精确指向同链主合同或补充协议。`contracts_termination_target_coherence_check` 保证非解除协议目标为空且解除协议不能指向自身；`idx_contracts_termination_target` 支持目标反查，`idx_contracts_active_termination_target` 保证同一目标最多存在一份未拒绝、未终止且未删除的办理中或已生效解除协议；目标同链、关系和有效状态继续由事务锁校验；
- 合同、发票、回款、付款金额使用 `NUMERIC(18,2)`（18 位精确数值），数据库限制绝对金额不超过 999999999999.99；历史存在超范围数据时先约束新数据并告警，历史清理后再验证约束；
- 主合同原始金额写入 `original_contract_amount` 后不再被补充协议覆盖；根合同当前有效金额由 `current_effective_amount` 保存。补充协议在审批时冻结“生效前金额＋本次增减额＝生效后金额”，归档生效时在根合同事务锁内校验前值并原子推进当前金额；仅付款协议保存 0 增减且前后金额相同，明确写明的最终总额优先反算本次增减。历史数据迁移才允许按生效顺序滚动回填快照，不再把运行时直接汇总 `amount_delta` 作为正式链条真值；
- 解除协议不新增结算或分摊表，复用 `amount_before_change`、`amount_after_change` 和 `amount_delta` 分别保存解除前金额、截至解除日已履行金额和“已履行减解除前”的非正调整额；全额履行时允许调整额为 0。主合同解除归档时把最终履行金额写回根合同 `current_effective_amount` 并终止根合同；补充协议解除只用未履行部分调整根合同当前金额并终止目标补充协议。历史财务表和回单记录不删除；
- `contracts.status` 允许独立的 `rejected`（已拒绝）和 `terminated`（已终止）终态。解除协议审批驳回只把解除协议自身置为已拒绝，被解除目标不改变；解除协议审批通过后自身进入待盖章，盖章归档事务才写入目标 `terminated_at`（终止时间）。历史原因式终止审批的 `pending_action`（待处理动作）和 `previous_status`（前序状态）继续兼容读取，但新请求不再写入；
- 根合同状态为 `rejected` 时，该合同组从项目合同总额、履约完成率、发票／回款／付款聚合、核算收入和经营看板中排除。历史财务事实表记录继续保留用于审计；`rejected` 与 `terminated` 分别统计，不得把已拒绝记录归入终止合同；
- `contracts.area`、`declared_category`、`declared_subtype`、`relation_type` 及资产类兼容 `asset_category` 在上传创建草稿时写入并锁定。主营二级分类只允许工程咨询、前期手续、技术咨询；非主营只允许非主营收入、其他服务；资产只允许采购、软件、设备、房屋租赁、汽车租赁、车位合同、办公资产，资产兼容字段必须与二级分类完全一致。`project_id` 外键关联 `worklog_projects`，仅供主营和非主营合同可选归属；数据库约束保证资产类项目编号为空，并在迁移时清理历史资产项目关系。项目归属与 `parent_contract_id` 的合同层级关系相互独立；保存时在事务中重新读取 `worklog_projects.district` 并与 `contracts.area` 严格比较。补充协议和终止协议校验上级合同的行政区、大类、二级分类和资产子类一致；主合同不查询上级并强制清空残留上级编号。任一不一致均拒绝，不得将项目或上级合同值写入覆盖当前合同。历史资产记录可按有效 `asset_category` 确定性回填二级分类；历史主营或非主营缺失值不得猜测，提交时安全阻断。正式金额或状态变化时，事务按每个有效根合同的 `current_effective_amount` 更新 `worklog_projects.contract_total_amount` 和合同状态快照，同一补充协议不得重复计入。

#### 文件、识别与盖章核验

- `contract_files(contract_id, file_hash)` 阻止同合同重复文件；条件唯一索引保证草拟合同、系统生成用印申请、三联单和请款单等版本化文件每类只有一个当前版本，并保证每份合同只有一个当前盖章版；
- `contract_seal_applications` 以合同版本绑定签名事实。用印申请签名后合同内容变化时，提交门禁会拒绝旧签名；新申请保留旧版本供审计，但只有当前已签名记录可作为送审证据。总经理通过首次用印审批时，申请人原始已签文件继续由 `signed_file_id`（申请人已签文件编号）保留，新增双签 PDF（便携式文档格式）由 `approved_file_id`（审批完成文件编号）指向并成为当前用印申请文件；审批轮次、审批人及审批签名快照字段必须全部为空或全部完整，且审批人角色必须为总经理。三联单和请款单不再是草拟用印提交必需件，可在实际付款阶段作为合同附件补充；
- 2026-08-14 起，总经理完成用印审批签署后，`signed_file_id`（已签文件编号）与 `approved_file_id`（审批完成文件编号）统一指向最终双签申请单；申请人单独签字版的附件记录和物理文件在审批事务提交后删除，不再作为后台历史文件保留。申请人签名身份、签署时间及签名快照字段继续保留。
- 新上传的辅助材料不执行内容识别，不产生 `contract_ocr_jobs`、`contract_invoices`、`contract_receipts` 或 `contract_payments` 记录；全部合同、发票和回单只存入 `contract_auxiliary_files`，合同总额、项目总额、月度／年度收入查询都不读取辅助档案两表。旧库启动迁移显式补齐 `ocr_lines_json`、`error_message`、`retry_count` 和 `version` 四列，并显式删除历史“同包每类一个当前文件”及“同包仅一个当前合同”唯一索引；只保留 `UNIQUE(package_id, file_hash)`（同包文件摘要唯一）防重；
- `contract_download_request_no_sequence`（合同下载申请编号序列）生成 `HTXZ-YYYYMMDD-######`。下载申请状态严格限制为待审批、管理员待办、执行中、已完成、已驳回和已撤回；同一员工、同一合同同时最多存在一条进行中申请；
- 驳回或撤回后重提必须创建新的主表行、新编号、新单签申请单和新附件快照。第一条记录固定 `chain_id = id`、`attempt_no = 1`；后续尝试必须关联唯一的 `previous_request_id` 并递增次数。`UNIQUE(previous_request_id)`（上次申请唯一后继）、`UNIQUE(chain_id, attempt_no)`（申请链次数唯一）和活动申请部分唯一索引共同阻止双击、并发重提及新建绕过；旧申请只允许推进已读时间，业务内容、签名、审批意见和申请单不得覆盖；
- 员工只能把待总经理审批的本人申请变为 `withdrawn`（已撤回），状态一致性约束要求撤回时间存在且审批、批准签名和执行字段仍为空。撤回与总经理审批均锁定主行并校验 `version`，从数据库层避免两个决定同时成功；
- 提交时锁定合同及当前附件，并将合同和附件字段复制到下载申请快照。选定附件外键使用 `ON DELETE RESTRICT`（限制删除），物理下载前再次核验快照 SHA-256（安全散列算法），防止文件替换后下载与申请内容不一致；
- 申请人和总经理签名均从 `user_signatures`（用户锁定签名）复制为独立快照并保存摘要。申请表批准前指向申请人单签 PDF（便携式文档格式），批准后指向同页双签 PDF；客户端提交的签名图片不写入任何下载申请表；
- 已撤回最新叶子删除不改变表结构或外键删除动作：服务在同一事务内先写合同级最小删除审计，再按审计、附件快照、申请主记录顺序显式删除，以满足现有 `ON DELETE RESTRICT`（限制删除）约束。只将申请主表保存的申请单和独立签名快照路径交给事务后物理清理；共享 `user_signatures` 原件和 `contract_files` 原合同附件始终保留；
- 目标总经理在提交事务中要求数据库恰有一个活动 `general_manager`（总经理）账号；目标执行人要求恰有一个活动 `admin`（管理员）账号并形成姓名和业务职位快照。流程展示固定使用“总经理＋姓名”“管理员＋姓名”，不受人事档案中的其他岗位名称影响；其他高权限账号不能替代已快照指定的执行人；
- `contract_ocr_jobs(status, lease_expires_at, created_at)` 支撑按状态、租约到期时间和创建时间认领任务；工作实例令牌确保只有当前持有者可提交结果；
- `contract_ocr_lines` 按 `job_id`（任务编号）、`page_number`（页码）和 `line_index`（行序号）建立读取索引。任务完成事务会先替换当前任务的逐行结果，再写字段证据与合同自动采用结果；逐行数据只增加可追溯性，不参与现有字段解析或自动采用门禁；
- 替换草拟合同时，旧任务转为失败并清空令牌、租约；新文件生成新任务，旧任务无法覆盖当前版本；
- 新建识别任务、整份重试或替换草拟文件时先把甲方、乙方、项目名称、合同金额、合同类型和合同签订日期六个核心字段统一清空；识别结果先写任务证据，再在同一事务中检查六字段是否全部非空、未舍入最终验证值是否均严格等于整数 100，并校验独立证据、字段内与跨字段一致性及日期合法性。99.99、99.999 和任何小于 100 的值均失败，不得先舍入再比较；错误或冲突内容即使为 100 也失败。全部通过时才设置 `final_value` 并原子更新 `contracts`；任一字段或验证不合格时，六个核心字段继续全部为空，杜绝部分落库；
- `declared_category` 是上传前预选分类，只用于与 OCR `category` 做一致性验证，绝不能替代、预填或覆盖 OCR 最终值。补充协议和终止协议在识别成功前只保存同区上级合同关系等非核心关系数据；识别成功事务自动锁定上级合同并比较行政区、预选分类、OCR 分类及资产子类，全部一致时才随其他五个核心字段原子写入，不一致时整次转为未达标并清空六字段；
- 草拟合同签订日期没有上传日期、当前日期或推测值回退，历史人工日期及确认标记不能形成系统最终值，也不能绕过提交门禁；
- `contract_ocr_fields` 中历史人工确认相关列仅用于兼容旧数据，当前流程不读取这些标记放行，也不提供人工补录写入路径；
- 盖章核验状态保存识别失败、待差异说明、差异审批中、差异已通过、差异已拒绝、待归档、已归档和已替代等结果；差异审批驳回时写入 `difference_rejected`（差异已拒绝）终态，不得继续伪装为待补充说明；低可信、缺失或冲突结果不可进入待归档，只能重试或由新文件替代；
- 盖章核验逐字段保存审批快照与只读识别事实。仅盖章版合同日期未识别时按业务规则保存上传日期来源，此回退不用于草拟合同；其他关键字段不合格时不产生可归档最终值，高可信差异只通过差异复审状态流转，不允许直接篡改识别值。

#### 财务配对登记、三态、去重和费率快照

- `contracts.financial_direction` 在合同创建时由 `declared_category`（锁定合同大类）生成：主营和非主营为 `income`（收入），资产类为 `cost`（支出）；`financial_direction_source`（方向来源）保存 `contract_category`（合同分类），不再要求发票编号、确认人或确认时间。启动迁移覆盖回填全部已分类历史合同并由数据库检查约束保证方向与分类一致；
- `contracts.asset_funding_mode`（资产合同资金承担方式）只允许 `engineering_direct`（工程咨询直接付款）、`engineering_to_technology`（工程咨询划拨科技支付）、`technology_direct`（科技自行承担）或 `pending_review`（待核对）。`contract_payments` 保存会进入经营支出的直接付款／工程划拨；`contract_external_payments` 仅保存科技公司最终向合同对方付款的履约核销事实，不重复计入经营支出；
- `contract_financial_registrations`、`contract_invoices`、`contract_receipts`、`contract_payments` 默认状态均为 `draft`（草稿）。普通收入和直接付款登记创建时至少包含一张发票；工程咨询划拨科技模式允许先创建无发票的科技对外付款登记，因此 `invoice_ocr_job_id` 和 `invoice_record_id` 允许为空。付款事实保存后立即确认并更新合同付款进度，发票后续补入同一登记；可对应部分写入匹配表，未开票或金额不一致部分保留为差额，最终确认时要求完全闭合。`bank_ocr_job_id`、银行业务指纹及回款／付款首项引用继续作为历史兼容字段，全部凭证明细以批次明细表为准；`idx_contract_financial_registration_one_draft_per_contract` 部分唯一索引保证同一合同最多存在一笔草稿登记；
- 新登记在同一数据库事务中锁定两项已验证识别任务，创建登记批次、发票记录和回款／付款记录，并同时把两个任务置为已消费。任一步骤、主体配对、类型方向或去重检查失败，整组回滚，不得留下孤立发票、孤立回单或单边已消费任务；
- 登记状态表达整笔发票配对是否闭合，凭证状态表达单据事实是否已经发生，因此同一未闭合登记内允许发票为 `draft`（草稿）、已经保存的回款／付款为 `confirmed`（已确认）。银行凭证确认后立即参与完成率和经营统计，发票金额不重复计入收支；配对完全闭合后再确认发票和登记。只有尚无已确认银行凭证的纯发票草稿可以整组硬删除；存在实际结算的开放登记只能整组冲正，`reversed`（已冲正）保留事实但排除核算。没有登记编号的历史单条记录继续走旧生命周期兼容，不能自动补配或与新登记混用；
- 发票、回款、经营支出和最终对外付款四类财务事实通过唯一的 `financial_ocr_job_id` 关联服务端识别任务。登记明细的 `item_kind` 新增 `external_payment`（最终对外付款），同一张发票可分别与工程划拨和科技最终付款建立按分对应关系。确认内部划拨登记时，划拨合计、最终对外付款合计及两类分配合计必须各自完整覆盖发票合计；
- `contract_financial_ocr_jobs.snapshot_json` 中新发票快照只保存购买方名称、销售方名称、开票名称、发票号码、开票日期、税费、开票金额七项和真实格式；开票名称沿用 `itemName`（开票名称字段）保存，并完整保留票面税收分类前缀和明细名称。双方税号、金额符号和凭证状态只作为识别期间的服务端安全证据，不写入页面业务快照。银行回单新快照只保存电子回单号码、付款时间、付款人户名及账号、收款人户名及账号、金额七项和真实格式。付款时间可为 `YYYY-MM-DD`（年月日）、`YYYY-MM-DD HH:mm`（年月日时分）或 `YYYY-MM-DD HH:mm:ss`（年月日时分秒），按原件精度保存，不补造原件未提供的时分秒，也不使用记账日期、上传日期或当前日期兜底；`evidence_text_hash` 保存识别正文摘要，`blocking_reasons_json` 保存结构化阻断原因，禁止写入完整识别正文；
- 财务识别仅允许当前 `worker_token`（工作令牌）提交完成或失败结果并在终态清空租约；相同摘要处于基础设施失败或租约过期时可接管原任务并增加 `retry_count`，业务阻断、文件错误及普通识别失败不得自动反复重跑。旧工作实例晚到结果因令牌不匹配而拒绝写入；
- `contract_financial_file_hashes.file_hash` 对发票、回款和付款原件执行跨合同全局唯一保护，文件名不参与判定；
- 新登记要求电子回单号码非空，并使用规范化电子回单号码、付款时间、金额、付款／收款人及双方账号生成 `bank_business_key_hash`（银行业务指纹）；登记表对该指纹建立唯一约束并配合事务锁阻止并发重复。历史无登记编号记录继续按电子回单号码、日期、金额及双方账号兼容检查；交易流水号、银行和币种不再是新登记字段或防重门禁，不得把含义不明的旧号码猜测写成电子回单号码；
- 发票按规范化后的销售方名称和发票号码建立跨状态条件唯一索引，草稿、已确认和已冲正记录均永久占用同一业务键；`deduplication_exempt` 只标记迁移前已经存在的历史重复数据，不能用于新记录绕过校验；
- 新登记的银行业务指纹与财务原件摘要跨合同全局防重，重复记录直接拒绝；客户端 `confirmDuplicate`（重复确认）标记不能绕过；
- 发票组合唯一索引及回款重复查询统一使用数据库 `NORMALIZE(..., NFKC)`（兼容等价规范化）、小写化和去空白表达式；迁移会先标记历史重复豁免记录，再重建索引，避免旧索引定义漂移；
- 资产付款 `expense_category` 只允许 `rent`、`electricity`、`parking`、`car_rental`、`internet`、`other` 六个编码；
- 已确认回款在确认时保存业务日期对应的税费、预扣营销、商务费用和财务成本费率快照；启动迁移为没有快照的历史已确认回款补齐匹配版本；
- 默认费率为税费 11.72%、预扣营销 5%、主营商务费用 10%、非主营财务成本 0.28%，费率检查约束只接受万分位精度。

#### 一致性、权限与审计

- 草稿更新、删除、撤回、盖章核验写操作使用 `contracts.version`；版本不一致时拒绝覆盖；
- 主营项目合同已关联项目时从 `worklog_projects.owner_user_id` 解析活动项目负责人，未关联项目时从唯一活动总经理解析审批人；非主营和资产类合同同样使用唯一活动总经理。已选项目无效、无法解析项目负责人、没有活动总经理或存在多个活动总经理时拒绝提交，不创建不确定的审批轮次；
- `contract_approval_rounds` 在提交事务中固定审批人账号、姓名、角色和来源。项目负责人、项目归属或总经理配置后续变化不改写正在审批及历史轮次，撤回或完成后重新提交才按最新配置创建新快照；
- 审批决定必须同时命中当前待审批轮次和 `target_approver_id`，角色相同但账号不同不能代办；待办查询按指定审批人和待审批状态过滤，已处理查询按该账号参与的历史轮次过滤；
- 审批动作 `reject`（驳回）在同一事务内清空待处理动作、关闭审批轮次并同步项目金额快照。普通用印、解除协议和盖章差异复审驳回时只把当前送审协议置为 `rejected`（已拒绝）；解除目标状态不变。`terminated`（终止）只由盖章解除协议归档事务写入，不能由普通审批决定直接产生；
- 用印、终止和盖章差异复审共用上述轮次与审批人解析规则；条件唯一索引保证每份合同同时至多存在一个 `pending`（待审批）轮次；
- 合同状态、审批记录、项目金额快照、核验状态和审计日志在同一 PostgreSQL（关系数据库）事务中提交；根合同组审批和财务防重使用事务级咨询锁串行化；
- 合同软删除使用 `is_deleted` 和 `deleted_at`，财务冲正保留原记录；未消费的临时财务凭证及未确认的财务登记草稿允许按依赖顺序硬删除事实记录、对应关系、识别任务、全局摘要和附件索引，以释放跨合同重复占用。审计日志只保留删除动作与业务编号，不以外键继续占用被删凭证；已确认、已冲正及已进入核算的记录仍完整保留；
- 常用查询分别按项目、根合同、父合同、分类／状态、创建时间、文件摘要、识别状态、盖章核验状态、财务状态／日期、费率生效日期和审计时间建立索引。

`reimbursements`（报销表）与 `payment_batches`（付款批次表）使用 `payment_business_date DATE` 保存银行回单实际交易日期。管理员确认付款后的 `paid` 状态允许该字段为空；上传回单后，`payment_uploaded`／`completed` 报销和 `uploaded`／`confirmed` 付款批次必须具有该日期。数据库不再按管理员操作时间自动回填，也不保留自动换算触发器；既有历史值原样保留，缺失值由重新识别或人工核对补齐。两表均建立按回单交易日期和状态过滤的月报索引。

月报继续只有一般、商务、福利一、福利二四个资金账户，不新增基本资金账户。基本账户只是 `monthly_financial_bank_files.account_code = 'basic'` 的物理来源，仅为薪资和商务报销提供银行事实；其利息、半年费及其他手续费分类为忽略，不进入资金账户公式。手工分类白名单和 `monthly_financial_manual_rule_is_valid`（月报手工分类映射函数）保持一般／商务利息与手续费分类，不新增基本账户对应分类。

月报报销补挂不新增业务主表：继续使用 `payment_batches`、`payment_batch_items`、`payment_proof_hashes`、`reimbursements`、`approval_records` 和 `monthly_financial_bank_transaction_links`。首次挂载在同一月报事务内共同写入批次、快照明细、防重身份、报销状态、审批记录及指向具体报销／付款批次的有效展示链接。既有凭证换版不删除或改写旧防重行；规范化回单号仍归属原付款批次，新裁片摘要以同批次的摘要证据保存，旧路径和日期进入链接 `match_key_json`（匹配键）及月报审计。链接的 `allocated_amount`（分配金额）保证多回单或多报销的整数分金额闭合。

`payment_proof_hashes.proof_no`（付款凭证回单号）迁移统一执行 NFKC（兼容等价规范化）、移除非 ASCII（美国信息交换标准代码）字母数字并大写，随后建立同表达式条件唯一索引 `uq_payment_proof_no_normalized`。迁移先聚合检查规范化冲突；发现冲突时抛出 `PAYMENT_PROOF_NORMALIZED_CONFLICT` 并停止初始化，禁止只保留原文唯一索引后继续运行。文件摘要继续全局唯一；合法同批换版保留旧摘要行，新裁片摘要另存为同批证据且空逻辑回单号，逻辑回单数量只统计非空回单号。

#### 审批中心银行回单与付款批次原子一致性

本次不新增数据表，继续使用既有 `bank_receipt_batches`、`bank_receipts`、`payment_batches`、`payment_batch_items`、`payment_proof_hashes`、`reimbursements` 和 `approval_records`。整包识别后的每张回单各自使用一个数据库 `transaction（事务）`；自动匹配和待认领手工关联共用同一写入边界，回单行、批次及其明细快照、报销状态、付款业务日期、防重身份和审批记录必须共同提交或共同回滚。

- 回单必须只有一个合法的银行实际交易日期；回单金额、报销净额、批次总额和批次明细均先转换为整数分比较，禁止用浮点近似通过。
- 每个目标报销单在事务内加行锁，并同时复核申请人收款姓名与完整账号。没有批次时只接受 `paid（已确认付款）` 报销单，事务自动创建状态为 `uploaded（已上传回单）` 的 `payment_batches` 及对应 `payment_batch_items`；已有唯一 `pending（待处理）` 批次时，成员必须与批次快照完全相同，明细与总额严格闭合，全部报销单属于同一收款人且状态只能是 `approved（已审批）` 或 `paid（已确认付款）`。
- `payment_proof_hashes` 同时保存回单裁片 SHA-256（安全散列算法）摘要和规范化电子回单号；服务在事务内串行查重后才消费防重身份。未匹配回单只原子写入 `bank_receipts`，不提前占用防重记录，待管理员认领成功时再与付款事实一并写入。
- 手工认领对既有 `unmatched（待认领）` 回单加行锁，并从 `ocr_raw_json` 读取权威账号、回单号和交易日期证据；旧记录缺少完整证据时拒绝关联。自动候选的业务复核失败先回滚全部付款写入，再单独原子保存为待认领；数据库异常保持失败，不留下半提交数据。
- 申请人按 `payment_batches` 确认收款；批次快照内的 `payment_uploaded（已上传回单）` 报销单和批次状态在同一事务中完成，避免单笔确认造成同批状态分裂。

数据库新增真实日期、四账户金额对象以及月报手工分类—账户—方向映射校验函数。相关约束先以 `NOT VALID`（不回扫存量）安装保护新写入，再在数据满足条件时执行验证；合同回款与资产付款业务日期同步增加真实日期约束和月度部分索引。

启动初始化会删除并重建 `monthly_financial_manual_items_category_check`（月报手工项目分类校验约束），确保已有数据库的分类白名单同步包含福利账户一、福利账户二的补充收入和全部支出分类；该升级可重复执行，不改写已有手工项目。

银行原件替换采用版本切换，不执行覆盖写入：同月同账户上传新完整文件时，事务先把旧文件改为非当前并记录替换时间，再插入递增版本的新文件。页面转换、拆分或 OCR（光学字符识别）不完整的候选文件仍在事务前拒绝。主营收入和资产支出未匹配已确认合同收付款时，银行交易以 `review_required（待复核）`和 `include_in_report = FALSE`保存，文件转为 `partial（部分待核对）`；一般／商务账户中识别确定的利息和跨行手续费保持计入。`chargeAccounts`仅接管费用类字段，`activeAccounts`仍只代表完整文件的全量业务接管。规范化回单按电子回单号复用稳定主键，旧文件行和原件继续保留。

合同回款、合同付款或科技最终对外付款由已确认转为已冲正时，数据库触发器在同一事务中停用对应月报链接，把当前银行交易改为 `review_required`（待复核）并排除经营收支，把活动文件改为 `partial`（部分识别），再按当前有效交易重新计算已计入笔数。任何一步失败都会随合同冲正事务整体回滚，不会留下“链接已失效但交易仍计入”的中间状态。

月报严格链接读取合同财务事实时持有共享行锁，合同冲正使用排他行锁，避免触发器与新链接交错遗漏。管理员复核排除后，交易改为 `ignored`（忽略）、文件在没有其他待复核交易时恢复为已识别，月报版本和审计日志同步提升；数据库不删除原交易、原文件或历史链接。事务提交阶段出现连接级不确定错误时会标记 `commitOutcomeUncertain`（提交结果不确定），上传路由保留稳定原件并要求按摘要刷新核对，不把它当普通回滚清理。

同一内部划转回单号若同时出现在两个账户原件中，只保留一条规范交易，并使用 `monthly_bank_file` 文件出现链接记录两个活动原件、各自页位与裁片。任一账户文件替换时只停用该文件的出现链接；仍有另一活动原件时规范交易自动回退到其证据，不会因一侧换版丢失另一侧流水。员工姓名与完整收款账号唯一命中时另建 `employee_profile` 分类链接，为逐人工资及报销提供稳定人员编号。

银行回单相关唯一规则全部通过可重复创建的索引执行：`uq_monthly_financial_bank_files_active` 阻止同月同账户存在两份当前文件，`uq_monthly_financial_bank_files_month_hash` 阻止同一报表月重复使用相同原件摘要但不占用其他月份，`uq_monthly_financial_bank_receipt_no` 仅对非空规范化电子回单号执行全局唯一，`uq_monthly_financial_bank_link_active` 阻止同一回单重复建立相同的当前业务链接。启动迁移先移除旧版文件摘要全局唯一约束，再幂等创建报表月联合唯一索引。原始完整账号均以 `TEXT`（文本）保存，不转数值、不截断前导零，也不使用尾号模糊匹配。

```typescript
const createProject = db.transaction((projectData) => {
  // 插入项目
  const project = db
    .prepare(
      `
    INSERT INTO projects (name, type, created_by)
    VALUES (?, ?, ?)
  `,
    )
    .run(projectData.name, projectData.type, projectData.userId);

  // 插入关联的事件
  const eventStmt = db.prepare(`
    INSERT INTO calendar_events (title, project_id, created_by)
    VALUES (?, ?, ?)
  `);

  projectData.events.forEach((event) => {
    eventStmt.run(event.title, project.lastInsertRowid, projectData.userId);

  return project.lastInsertRowid;
});

}
```

脚本默认将备份写入桌面统一换机目录的 `YuliLog换机备份/02-自动更新备份/`，同时处理：

- 生产模式 PostgreSQL（关系型数据库）容器 `yulilog-postgres-prod`
- 开发模式 PostgreSQL（关系型数据库）容器 `yulilog-worklog-postgres`

- 开发模式独立的 `uploads/development/` 上传目录
- 旧共享目录中无法根据数据库判断归属的 `uploads/unassigned/` 历史文件目录
- `.env`、当前代码、未提交修改和部署配置

目录结构：


配置移动硬盘后，在 `移动硬盘目标.txt` 第一行写入目标路径，例如：

```text
/Volumes/YuliLogBackup/YuliLog换机备份
```

脚本会从 `docs/YuliLog换机重建说明.txt` 自动覆盖更新备份根目录中唯一的 `换机说明.txt`，并在文档末尾写入更新时间及当前构建文件的 SHA-256（文件校验算法）校验值。构建文件或依赖清单发生变化后，下一次成功备份会直接更新这一份说明，不单独保留说明的历史版本。容器镜像不再单独导出；换机时由 Claude（开发助手）或 Codex（开发助手）读取该说明，并依据备份项目中的 Dockerfile（容器构建文件）、编排文件及依赖清单联网重建生产、开发和 OCR（文字识别）环境。

生产容器将 `uploads/production/` 挂载为容器内的 `/app/uploads`，开发容器将 `uploads/development/` 挂载为容器内的 `/app/uploads`，因此现有 API（应用程序接口）和数据库文件路径不需要修改。一次性迁移脚本 `scripts/split-upload-directories.sh` 会根据生产与开发数据库中的文件引用划分旧共享文件；两个数据库共同引用的文件分别保留一份，没有数据库引用的历史文件移入 `uploads/unassigned/`，避免混入正式生产目录，同时确保不丢弃旧文件。

各环境内部继续按 `业务类别/年/月/日/文件` 分类，日期取中国时区的实际上传时间，不使用发票开票日期等业务日期。`scripts/migrate-uploads-to-date.sh` 根据旧文件保存时间迁移现有文件，并同步更新生产与开发数据库中的路径引用；`scripts/migrate-backup-history-to-date.sh` 将原有数据库、项目、完整快照和运行日志迁移到年/月/日目录。

目标可用时，整个 `YuliLog换机备份` 会增量同步到移动硬盘。移动硬盘未连接时不会中断本机备份，日志会记录目标不可用。严格意义上的实时容灾仍依赖异机或移动硬盘副本；仅保存在本机桌面的自动备份无法防止本机硬盘整体损坏。

当前服务器已创建名为 `YuliLog每小时自动备份` 的 Codex（人工智能编程助手）本地自动任务，每小时调用一次备份脚本并检查数据库校验结果和容器运行状态。自动任务失败时不会删除上一次成功备份，只报告错误原因。

自动备份在改写 `latest` 前会校验三类持久附件均符合“业务类别/年/月/日/文件”结构；发现未日期化业务附件时立即失败，从而保留上一次成功快照。生产、开发环境的 `temp` 临时处理目录和三类目录中的 `.DS_Store` 系统元数据不属于可恢复业务附件，不写入备份，并会从 `latest` 清除旧残留。第二次附件同步后还会复核备份副本，并实时生成包含“分类状态：已完成”、校验时间和三类附件数量的状态文件。

## 注意事项

1. **并发控制**：
   - PostgreSQL 支持并发读写
   - 使用 WAL 模式提高并发性能
   - 长事务会阻塞写操作

2. **数据类型**：
   - PostgreSQL 是强类型
   - 建议在应用层严格验证
   - 使用 TEXT 存储 JSON 数据

3. **备份策略**：
   - 定期备份数据库文件
   - 重要操作前手动备份
   - 测试恢复流程

4. **性能监控**：
   - 分析慢查询
   - 定期 VACUUM 清理
   - 监控数据库文件大小

## 开票申请数据表

### `invoice_applications`（开票申请表）

- 以 `application_no`（申请编号）作为唯一业务编号，`contract_id`（合同编号）必须指向主营或非主营主合同。
- 申请创建时固化合同编号、名称、大类、行政区、甲方和当前有效金额快照，后续展示历史申请时不从变动的合同主数据猜测旧值。
- `amount`（本次开票金额）必须为正数，表示客户拟支付金额，不产生我公司付款记录。
- `material_mode`（材料模式）只能为 `material_need_seal`（有材料需盖章）、`material_no_seal`（有材料不需盖章）或 `no_material`（无材料）。主营合同固定为第一种，非主营由申请人选择。
- 开票信息单独保存名称、税号、地址、电话、开户行、账号和备注；`billing_original_json`（开票信息原值）保存历史带入值，供审计修改差异。
- 状态仅允许 `draft`（草稿）、`pending_approval`（待总经理审批）、`rejected`（已驳回）、`pending_seal`（待盖章交付）、`pending_invoice`（待开具发票）和 `completed`（已完成）。
- 申请人的部门、职位、姓名以及总经理的职位、姓名、签名路径、SHA-256（安全散列算法）摘要及时间按当次事实固化；管理员交付和开具完成也分别保存操作人快照及备注。
- `version`（版本）用于乐观并发控制；提交事务内还必须锁定根合同并重算可用额度。

### `invoice_application_materials`（开票申请材料表）

- 每份材料保存原文件名、存储路径、字节数、服务端确认的媒体类型、SHA-256（安全散列算法）摘要、是否需要盖章及上传人。
- `UNIQUE(application_id, file_hash)`（同申请文件摘要唯一）阻止同一原件在一份申请中重复上传。
- 新生成的主营三联单在 `invoice_applications` 保存 `triplicate_project_name`（三联单工程项目名称）、`triplicate_previous_payment_snapshot`（生成前累计）和 `triplicate_cumulative_payment_snapshot`（本次累计）三项快照；数据库约束强制“本次累计＝之前累计＋申请金额”。材料表以 `is_system_generated_triplicate` 标识系统三页 PDF，并通过每申请唯一索引保证只保留一份当前在线三联单。`has_other_expense_sheet` 继续兼容历史 Excel 三联单的结构校验事实。

### `invoice_application_generated_files`（开票申请生成文件表）

- `applicant_signed`（申请人单签）保存员工提交时生成的单页 A4（国际标准纸张）申请单，`approved`（审批双签）保存总经理通过时生成的同页双签申请单。
- 每个申请和文件类型使用递增 `version`（版本）保留历史，条件唯一索引 `idx_invoice_application_generated_current` 保证每类只有一份 `is_current=TRUE`（当前文件）。
- `invoice_applications.applicant_signed_file_id`（申请人单签文件编号）和 `approved_file_id`（审批双签文件编号）仅指向同申请的当前文件。草稿内容变化后旧文件改为非当前但仍保留审计，不覆盖旧文件。
- 数据库只保存受控路径和 SHA-256（安全散列算法）摘要；预览接口必须重算物理文件摘要并与记录一致后才输出。

### `invoice_application_invoice_allocations`（开票申请与正式发票分配表）

- 关联现有 `contract_invoices`（合同发票），保存本次申请由已有正式发票覆盖的金额。
- 同一申请和发票组合唯一，分配金额必须为正数；正式发票冲正时对应分配必须失效或扣回，不得继续占用“已开票”金额。
- 分配按“申请提交时间／申请编号”和“正式发票建档时间／发票编号”执行 FIFO（先进先出），且发票不得覆盖在其建档之后才提交的新申请。全程按分计算。
- 正式发票冲正或删除时使用外键级联删除分配事实，服务在根合同行锁中重建 FIFO（先进先出）分配；只有 `issued_at`（管理员已登记开具时间）存在且正式发票足额时才能完成。失去足额发票覆盖的已完成申请自动回开为待财务登记，审计链不删除。

### `invoice_application_audit_logs`（开票申请审计表）

- `withdraw`（员工撤回）记录申请人在总经理处理前将待审批申请恢复为草稿；审计记录保留撤回前后状态、操作人和时间，不删除原提交记录。

- 保存草稿创建／更新、材料增删、提交、通过、驳回、盖章交付、已开具登记、正式发票分配、自动完成和冲正回开等操作。
- 每条记录固化操作人姓名、职位、前后状态、说明及最小必要元数据；不保存完整三联单文本或不必要个人数据。
