# 08 - 数据库模块

## 模块概述

数据库模块负责 PostgreSQL 数据库的初始化、表结构定义、数据迁移和种子数据管理。

## 主要功能

### 1. 数据库初始化
- PostgreSQL 数据库连接
- 表结构自动创建
- 索引和约束设置
- 默认数据填充

### 2. 数据表管理
- 用户表
- 项目表
- 工作日志表
- 日历事件表
- 事件库表
- 节假日表
- 会话表

### 3. 数据迁移
- 数据库版本管理
- 结构变更迁移
- 数据迁移脚本

### 4. 种子数据
- 初始化数据填充
- 测试数据生成
- 开发环境数据

### 1. Users（用户表）
```sql
CREATE TABLE IF NOT EXISTS users (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  email TEXT,
  feishu_user_id TEXT UNIQUE,
  feishu_username TEXT,
  avatar_url TEXT,
  role TEXT DEFAULT 'user',
  is_active BOOLEAN DEFAULT 1,
  last_login_at DATETIME,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_users_feishu_user_id ON users(feishu_user_id);
CREATE INDEX idx_users_role ON users(role);
```

#### 员工编号一致性
- `users.employee_no` 是账号员工编号的唯一数据来源，创建和编辑时必须填写
- 数据库通过条件唯一索引 `uq_users_employee_no` 阻止非空员工编号重复
- 用户接口修改编号时，在同一事务内同步 `employee_profiles.employee_no`
- 用户接口修改编号时不更新 `employee_documents.file_name`，已归档资料的文件名和文件内容保持管理员上传时的状态
- 数据库启动时不再为空编号账号自动补号；管理员必须在用户管理中填写
- 数据库启动迁移只用账号中的非空编号修复 `employee_profiles` 基础档案记录，不会改写 `employee_documents` 人事档案文件；入职模板下载优先读取账号中的最新值

```sql
CREATE UNIQUE INDEX IF NOT EXISTS uq_users_employee_no
ON users(employee_no)
WHERE employee_no IS NOT NULL AND BTRIM(employee_no) <> '';
```

### 8. LeaveBalances（假期余额表）
```sql
CREATE TABLE IF NOT EXISTS leave_balances (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id),
  leave_type_code TEXT NOT NULL REFERENCES leave_type_configs(code),
  year INTEGER NOT NULL,
  total_days NUMERIC(5,1) NOT NULL,
  used_days NUMERIC(5,1) NOT NULL DEFAULT 0,
  pending_days NUMERIC(5,1) NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE(user_id, leave_type_code, year)
);
```

**假期余额同步口径：**
- 假期类型默认天数变更时，仅同步当年 `total_days` 仍等于旧默认天数的余额记录
- 管理员手动调整过的个人余额不会被假期类型默认天数覆盖
- 调整个人余额时必须满足 `total_days >= used_days + pending_days`，检查和更新在同一事务内加行锁完成
- 启动迁移会识别“999 天且不校验余额”的旧版事假哨兵配置，改为每年 3 天带薪事假，并同步未发生使用或预占冲突的 999 天历史余额

### 8.1 LeaveRequests（请假申请表）
```sql
CREATE TABLE IF NOT EXISTS leave_requests (
  id TEXT PRIMARY KEY,
  request_no TEXT UNIQUE NOT NULL,
  user_id TEXT NOT NULL REFERENCES users(id),
  leave_type_code TEXT NOT NULL REFERENCES leave_type_configs(code),
  start_date TEXT NOT NULL,
  start_half TEXT NOT NULL,
  end_date TEXT NOT NULL,
  end_half TEXT NOT NULL,
  total_days NUMERIC(5,1) NOT NULL,
  balance_allocations_json TEXT,
  balance_reserved BOOLEAN NOT NULL DEFAULT FALSE,
  status TEXT NOT NULL DEFAULT 'pending'
);
```

**余额快照说明：**
- `balance_allocations_json` 保存申请提交时按自然年拆分的天数，跨年申请审批时分别结算对应年份余额
- `balance_reserved` 保存提交时该假期类型是否需要余额检查，避免管理员后续修改类型配置后造成预占天数无法释放或错误扣减
- 新提交和重新提交通过事务行锁预占 `pending_days`，审批、驳回、撤销再按快照转为已使用或释放

### 8.2 人力成本工资表
`employee_documents` 为劳动合同档案增加以下期限字段：

```sql
contract_start_date TEXT,
contract_end_date TEXT,
contract_recognized_at TEXT
```

- 同一员工可保存多条 `document_type='contract'` 的档案记录，构成续签历史
- `employee_documents.document_type='other'` 保存员工提供但不属于固定十类的其他资料；该类型允许同一员工保存多份文件
- `employee_profiles.contract_end_date` 是当前合同结束日期的查询快照，来源为合同档案中最大的 `contract_end_date`
- 不再根据 `hire_date` 推算合同到期时间；启动迁移会清理没有合同依据且恰好等于“入职日期加一年”的旧推算值

```sql
CREATE TABLE IF NOT EXISTS employee_salary_profiles (
  employee_id TEXT PRIMARY KEY REFERENCES employee_profiles(id) ON DELETE CASCADE,
  initial_monthly_salary NUMERIC NOT NULL CHECK(initial_monthly_salary >= 0),
  source_document_id TEXT REFERENCES employee_documents(id) ON DELETE SET NULL,
  recognized_at TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS payroll_records (
  id TEXT PRIMARY KEY,
  employee_id TEXT NOT NULL REFERENCES employee_profiles(id) ON DELETE CASCADE,
  payroll_month TEXT NOT NULL,
  automatic_salary NUMERIC NOT NULL DEFAULT 0 CHECK(automatic_salary >= 0),
  monthly_salary NUMERIC NOT NULL DEFAULT 0 CHECK(monthly_salary >= 0),
  contribution_base NUMERIC NOT NULL DEFAULT 0 CHECK(contribution_base >= 0),
  individual_income_tax NUMERIC NOT NULL DEFAULT 0 CHECK(individual_income_tax >= 0),
  monthly_salary_is_manual BOOLEAN NOT NULL DEFAULT FALSE,
  contribution_base_is_manual BOOLEAN NOT NULL DEFAULT FALSE,
  tax_is_manual BOOLEAN NOT NULL DEFAULT FALSE,
  updated_by TEXT REFERENCES users(id),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE(employee_id, payroll_month)
);
```

- 工资金额使用无固定小数位的 `NUMERIC`（精确数值），保留公式产生的完整有效小数
- 单位与个人承担明细不重复存储，由统一计算服务根据月度基础字段实时推导，避免公式修改后出现字段不一致
- 三个手工标记区分自动值和管理员改单值；普通自动重算不覆盖手工值，新上传正式邀请函时仅重置本月工资手工标记，缴费基数和个税手工标记不变
- 历史月份保留月度快照；员工删除时工资档案和月度记录随员工档案级联删除
- 一键删除人事档案时只删除该员工的 `employee_documents`，同时清空 `employee_profiles.contract_end_date`；`employee_salary_profiles` 与 `payroll_records` 保留，来源文件外键通过 `ON DELETE SET NULL` 自动置空
- 批量档案删除与合同日期清空在同一事务中完成；删除过劳动合同时，当前及未来自动工资按无合同档案状态重新同步，历史月份和管理员手工金额保持不变
- 数据库初始化会清理关联用户角色为 `super_admin` 的工资记录，系统维护账号不纳入人力成本数据

### 9. Human Resources（人事流程表）
```sql
CREATE TABLE IF NOT EXISTS probation_confirmations (
  id TEXT PRIMARY KEY,

  hire_date TEXT NOT NULL,

);

CREATE TABLE IF NOT EXISTS resignation_requests (
  id TEXT PRIMARY KEY,
  employee_id TEXT NOT NULL REFERENCES employee_profiles(id) ON DELETE CASCADE,
  employee_user_id TEXT NOT NULL REFERENCES users(id),
  handover_user_id TEXT NOT NULL REFERENCES users(id),
  handover_name TEXT,
  resign_type TEXT NOT NULL,
  resign_date TEXT NOT NULL,
  reason TEXT,
  status TEXT NOT NULL DEFAULT 'draft',
  employee_confirm_time TEXT,

  approver_comment TEXT,
  reject_target TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,

);

CREATE TABLE IF NOT EXISTS resignation_documents (
  id TEXT PRIMARY KEY,
  request_id TEXT NOT NULL REFERENCES resignation_requests(id) ON DELETE CASCADE,
  document_type TEXT NOT NULL,
  uploader_role TEXT NOT NULL,
  file_name TEXT NOT NULL,
  file_path TEXT NOT NULL,
  file_size INTEGER,
  mime_type TEXT,
  uploaded_by TEXT NOT NULL REFERENCES users(id),
  uploaded_by_name TEXT,

);

CREATE TABLE IF NOT EXISTS resignation_templates (
  id TEXT PRIMARY KEY,
  template_type TEXT NOT NULL,
  name TEXT NOT NULL,
  file_name TEXT NOT NULL,
  file_path TEXT NOT NULL,
  file_size INTEGER,
  mime_type TEXT,
  uploaded_by TEXT NOT NULL REFERENCES users(id),
  uploaded_by_name TEXT,
  created_at TEXT NOT NULL

```

**说明：**
- `probation_confirmations.employee_id` 使用唯一索引，确保每名员工只有一条当前转正记录；入职提交和转正记录创建在同一事务内完成
- 待处理的转正审批实例使用条件唯一索引，确保同一转正记录同时最多存在一个待审批实例
- `resignation_requests` 保存离职主流程，支持草稿、提交、交接确认、管理员审批等状态。
- `resignation_requests.reject_target` 记录驳回给离职人、交接人或双方；状态包含交接人被驳回后的独立待处理状态
- `resignation_documents` 按申请表、双方交接单、补充材料和上传角色区分离职材料，`is_current` 用于保留历史版本，也是员工详情“离职档案”Tab 的附件数据来源。
- `resignation_templates` 由管理员维护固定模板，除申请表与交接单外，还支持终止/解除劳动关系证明、固定资产交接单、离职经济补偿协议书、离职其他费用结算约定、合伙人离任分红结算模板。
- `resignation_requests.employee_id` 采用唯一约束，便于按员工维度聚合查询离职档案；若无离职申请记录，可结合 `employee_profiles.employment_status = 'resigned'` 做前端展示兜底。

## 数据库操作

### 基础查询
```typescript
import { db } from './db'

// 查询单条
const user = db.prepare('SELECT * FROM users WHERE id = ?').get(userId)

// 查询多条
const users = db.prepare('SELECT * FROM users WHERE role = ?').all('admin')

// 插入
const result = db.prepare(`
  INSERT INTO users (name, email, role)
  VALUES (?, ?, ?)
`).run(name, email, role)

const newUserId = result.lastInsertRowid

// 更新
db.prepare('UPDATE users SET role = ? WHERE id = ?').run(role, userId)

// 删除
db.prepare('DELETE FROM users WHERE id = ?').run(userId)
```

### 事务处理
```typescript
const createProject = db.transaction((projectData) => {
  // 插入项目
  const project = db.prepare(`
    INSERT INTO projects (name, type, created_by)
    VALUES (?, ?, ?)
  `).run(projectData.name, projectData.type, projectData.userId)

  // 插入关联的事件
  const eventStmt = db.prepare(`
    INSERT INTO calendar_events (title, project_id, created_by)
    VALUES (?, ?, ?)
  `)

  projectData.events.forEach(event => {
    eventStmt.run(event.title, project.lastInsertRowid, projectData.userId)
  })

  return project.lastInsertRowid
})

// 执行事务
try {
  const projectId = createProject(projectData)
} catch (error) {
  // 事务自动回滚
  console.error('创建项目失败:', error)
}
```

### 预编译语句
```typescript
// 提高性能，避免重复编译
const getUserStmt = db.prepare('SELECT * FROM users WHERE id = ?')

const user1 = getUserStmt.get(1)
const user2 = getUserStmt.get(2)
```

## 数据迁移

### 迁移脚本示例
```typescript
// server/db/migrations/001_add_user_status.ts
export const up = (db: Database) => {
  db.exec(`
    ALTER TABLE users ADD COLUMN is_active BOOLEAN DEFAULT 1;
    CREATE INDEX idx_users_is_active ON users(is_active);
  `)
}

export const down = (db: Database) => {
  db.exec(`
    DROP INDEX idx_users_is_active;
    ALTER TABLE users DROP COLUMN is_active;
  `)
}
```


## 数据备份与恢复

### 备份数据库
```bash
# 完整备份
pg_dump -U postgres yulilog_worklog > data/backup/worklog_$(date +%Y%m%d).sql

# 导出 SQL
pg_dump -U postgres yulilog_worklog > backup.sql
```

### 恢复数据库
```bash
# 从备份恢复
psql -U postgres yulilog_worklog < data/backup/worklog_20260122.sql

# 从 SQL 恢复
psql -U postgres yulilog_worklog < backup.sql
```

### 自动滚动备份

执行脚本：

```bash
bash scripts/automatic-backup.sh
```

脚本默认将备份写入桌面统一换机目录的 `YuliLog换机备份/02-自动更新备份/`，同时处理：

- 生产模式 PostgreSQL（关系型数据库）容器 `yulilog-postgres-prod`
- 开发模式 PostgreSQL（关系型数据库）容器 `yulilog-worklog-postgres`
- 生产模式独立的 `uploads/production/` 上传目录
- 开发模式独立的 `uploads/development/` 上传目录
- 旧共享目录中无法根据数据库判断归属的 `uploads/unassigned/` 历史文件目录
- `.env`、当前代码、未提交修改和部署配置

```text
└── 换机说明.txt                  # 供 Claude 或 Codex 按构建文件联网恢复环境
```

配置移动硬盘后，在 `移动硬盘目标.txt` 第一行写入目标路径，例如：

```text
/Volumes/YuliLogBackup/YuliLog换机备份
```

脚本会从 `docs/YuliLog换机重建说明.txt` 自动覆盖更新备份根目录中唯一的 `换机说明.txt`，并在文档末尾写入更新时间及当前构建文件的 SHA-256（文件校验算法）校验值。构建文件或依赖清单发生变化后，下一次成功备份会直接更新这一份说明，不单独保留说明的历史版本。容器镜像不再单独导出；换机时由 Claude（开发助手）或 Codex（开发助手）读取该说明，并依据备份项目中的 Dockerfile（容器构建文件）、编排文件及依赖清单联网重建生产、开发和 OCR（文字识别）环境。

生产容器将 `uploads/production/` 挂载为容器内的 `/app/uploads`，开发容器将 `uploads/development/` 挂载为容器内的 `/app/uploads`，因此现有 API（应用程序接口）和数据库文件路径不需要修改。一次性迁移脚本 `scripts/split-upload-directories.sh` 会根据生产与开发数据库中的文件引用划分旧共享文件；两个数据库共同引用的文件分别保留一份，没有数据库引用的历史文件移入 `uploads/unassigned/`，避免混入正式生产目录，同时确保不丢弃旧文件。

各环境内部继续按 `业务类别/年/月/日/文件` 分类，日期取中国时区的实际上传时间，不使用发票开票日期等业务日期。`scripts/migrate-uploads-to-date.sh` 根据旧文件保存时间迁移现有文件，并同步更新生产与开发数据库中的路径引用；`scripts/migrate-backup-history-to-date.sh` 将原有数据库、项目、完整快照和运行日志迁移到年/月/日目录。

目标可用时，整个 `YuliLog换机备份` 会增量同步到移动硬盘。移动硬盘未连接时不会中断本机备份，日志会记录目标不可用。严格意义上的实时容灾仍依赖异机或移动硬盘副本；仅保存在本机桌面的自动备份无法防止本机硬盘整体损坏。

当前服务器已创建名为 `YuliLog每小时自动备份` 的 Codex（人工智能编程助手）本地自动任务，每小时调用一次备份脚本并检查数据库校验结果和容器运行状态。自动任务失败时不会删除上一次成功备份，只报告错误原因。

自动备份在改写 `latest` 前会校验三类持久附件均符合“业务类别/年/月/日/文件”结构；发现未日期化业务附件时立即失败，从而保留上一次成功快照。生产、开发环境的 `temp` 临时处理目录和三类目录中的 `.DS_Store` 系统元数据不属于可恢复业务附件，不写入备份，并会从 `latest` 清除旧残留。第二次附件同步后还会复核备份副本，并实时生成包含“分类状态：已完成”、校验时间和三类附件数量的状态文件。

## 性能优化

### 1. 索引优化
```sql
-- 复合索引
CREATE INDEX idx_worklogs_user_date
  ON worklogs(user_id, log_date);

-- 覆盖索引
CREATE INDEX idx_users_role_active
  ON users(role, is_active);
```

### 2. 查询优化
```typescript
// 使用参数化查询
const stmt = db.prepare('SELECT * FROM users WHERE role = ?')
const admins = stmt.all('admin')

// 限制返回字段
const users = db.prepare(`
  SELECT id, name, role FROM users
`).all()

// 分页查询
const page = 1
const pageSize = 20
const offset = (page - 1) * pageSize

const users = db.prepare(`
  SELECT * FROM users
  LIMIT ? OFFSET ?
`).all(pageSize, offset)
```

### 3. 批量操作
```typescript
// 批量插入
const insertMany = async (holidays) => db.transaction(async (client) => {
  for (const h of holidays) {
    await client.query(
      `INSERT INTO holidays (id, date, name, type, year, source_url, created_at, updated_at)
       VALUES ($1, $2, $3, $4, $5, $6, $7, $8)
       ON CONFLICT(date) DO UPDATE SET
         name = excluded.name,
         type = excluded.type,
         source_url = excluded.source_url,
         updated_at = excluded.updated_at`,
      [h.id, h.date, h.name, h.type, h.year, h.source_url, h.created_at, h.updated_at]
    )
  }
})

await insertMany(holidayData)
```

### 4. 节假日数据自动维护

- `holidays` 表仍是日历、日志、请假工作日计算和周报定时任务的统一数据源
- `server/services/holidayUpdater.ts` 会自动发现国务院办公厅年度节假日通知，解析放假日和调休上班日后 `upsert` 到 `holidays`
- 服务启动后自动检查一次，并每天 03:10 检查今年和明年是否缺少数据
- `npm run update:holidays 年份` 保留为手动兜底命令，默认强制刷新指定年份
